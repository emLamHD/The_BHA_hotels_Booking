# ADR 0011: One activity stream per Admin menu and per-Staff unseen badges

- Status: Proposed (work item `BHA-ADMIN-BADGE-001-PR01`, 2026-11-20). Waiting for Owner acceptance of this revised text. The Owner decided two points on 2026-11-20 (D1 and D2, recorded under "Decisions"); the ADR as a whole is **not** `Accepted` until the Owner says so. **Nothing below is implemented** except where a section says "exists".
- Date: 2026-11-20
- Related: ADR 0007 (Staff identity, Property memberships), ADR 0008 (global website permission), ADR 0009 (per-Property promotion permission), ADR 0010 (global Blog permissions). This ADR adds **no permission, role or Staff column** and amends none of them: every permission below is read from the code that exists today.

## Context

`BHA-NEWSLETTER-BADGE-001` (PR #136, merged) gave the Newsletter menu a per-Staff "unseen" badge. The Owner (2026-11-20) wants the same for every Admin menu that matters, with the rules in §Product rules. What exists, verified in source:

- **Tables** (migration 25): `MenuActivityStreams(MenuKey PK, LastSequence)`, `NewsletterVerificationActivities(Sequence PK, SubscriptionId FK **cascade**, OccurredAtUtc)` and `StaffMenuSeen(StaffAccountId, MenuKey PK; LastSeenSequence; FK to the stream Restrict, to `StaffAccounts` cascade)`.
- **One recorder**: `NewsletterActivityLog.RecordVerifiedAsync` takes the next number with `UPDATE "MenuActivityStreams" … RETURNING` and inserts in the same transaction as the verification. The counter row stays locked until COMMIT, so numbers commit in the order given, and "everything up to N is committed" is true for a reader that sees N. Its lock order is subscription, mails, then the counter row.
- **Count by rows**: `MenuUnseenService` counts `count(*) where Sequence > cursor` and reads counter, cursor and count in one statement. This is right for the Newsletter as it exists: a verification is one physical row and one event, there is no correlation and no baseline date, and a Staff with no cursor counts from 0. `MarkSeenAsync` is one `INSERT … ON CONFLICT DO UPDATE` with `GREATEST`, refused above the counter.
- **API** (`AdminWebsiteMenuUnseenController`): `GET /api/admin/v1/website/menu-unseen` → `{ newsletter: { count, lastSeenWatermark, currentWatermark } }`; `POST …/menu-unseen/{menuKey}/seen { viewWatermark }` → 200, `400 menu-unseen-watermark-invalid`, `404 menu-unseen-unknown-menu`. **Both carry `StaffWebsitePermission(WebsiteSettingsManage)`**, and `MenuUnseenKeys.IsKnown` accepts only `newsletter`.
- **Live**: `NewsletterLiveHub` is a server-to-client pipe for one message (`newsletterVerified`), authorized at connect and again at every send, with in-process connections (no backplane).
- **Admin_Web**: `NewsletterBadgeProvider` mounts once in the layout; the count comes from the API (SignalR is a hint, polling every 30 s, BigInt comparison, answers older than the applied one are dropped, a new generation per Staff identity). The sidebar shows `99+` on the Newsletter item and a **dot** (not a number) on the parent.

What blocks generalising it as is:

1. A Blog-only Staff or a Promotions Manager gets 403 from `menu-unseen`, because the route needs `WebsiteSettingsManage`.
2. Promotions and Calendar live under `/properties/{propertyId}/…`, Catalog under `/catalog`; `/website` does not fit them.
3. `StaffMenuSeen` has primary key (Staff, MenuKey); it cannot hold a per-Property cursor without a new table.
4. `StaffCalendarModeGuard` opens a route in `Staff` mode only for `StaffCalendarPermissionAttribute`, `StaffWebsitePermissionAttribute`, the Newsletter hub marker or the three session actions. There is no session-only marker, and a cross-menu read has no single permission.
5. Deleting a subscription deletes its activity (cascade), which contradicts rule 3 below.
6. The Calendar segment id is **not** a stable identity: `AssignmentMutationStore` supersedes the old segments and creates new ones with `Guid.NewGuid()` on move and split.
7. `UseNpgsql` is configured without `EnableRetryOnFailure`; the Blog posts service and the Newsletter admin service already wrap writes in `Database.BeginTransactionAsync`. Other services, including Catalog, Promotions, Hero and Menus, were not read for their transaction use and are PR-6 to PR-12 work (see Rollout).

## Product rules (decided by the Owner; not reopened here)

1. Every Staff has a number per menu: events by **other** people after the Staff's own "seen" point; their own actions do not count.
2. Add, edit, delete and publish all count, **by logical event**: editing a post five times is 5; only one Save-then-Publish chain (rule 6) collapses two physical rows into one event.
3. Add then delete keeps every event and stays viewable; each event keeps a safe title snapshot and does not depend on the object existing.
4. A parent menu shows the **real sum** of the children the Staff may see, never a sum of formatted `99+` strings. Dashboard, Forms, Tables, Charts and UI Elements (template) have no badge.
5. Clicking the badge opens the unseen list and does **not** mark anything seen. At most 50 newest entries, grouped by person and object; when more exist it says `50+` and links to history. A number is acknowledged only after the menu page loaded its data successfully, with the watermark tied to the data it read.
6. One Save-then-Publish click on the Blog with the same `correlationId` is one aggregate event; `BlogAudits` still records every operation. A failed publish leaves the saved event in place.
7. Calendar is the exception: its number counts **unread bars/objects**, not mutations; another person's change highlights the bar in one fixed colour; opening the page does not acknowledge the board; clicking exactly one bar acknowledges the version of that bar that was observed. An object that has vanished (a cancel) stays in the unread list with its own "mark seen" button (decision D1).
8. Newsletter moves to the shared standard in PR-14; Admin add and delete create events then.
9. History is kept long term, with no retention job. A new menu starts at 0 when its recording is activated; no arbitrary backfill.
10. A Staff with no cursor counts only events at or after the creation of their account (decision D2); the history screen is not filtered by that date.

Defaults taken from the plan (assumptions, change them by amending this ADR): the sidebar keeps `99+` and the list window uses `50+`; a bulk picture upload is **one** event whose item count is the number of pictures; `correlationId` merges only the Blog save-then-publish chain in this phase.

Out of scope and not to be reinterpreted: counting objects on every menu, recording only "important" events, acknowledging on badge click, a bell or e-mail notification, or any other messaging system.

## Decision

### A. Model and invariants (proposed; migration in PR-2)

- **`AdminActivities`** (append-only). Primary key `(MenuKey, Sequence)`; `Id uuid` unique. Columns: `PropertyId uuid NULL` (set only for Property-scoped menus; FK `Restrict` to `Properties`), `ActorKind` (`Staff` | `Public` | `System`), `ActorStaffId uuid NULL` (FK `Restrict` to `StaffAccounts`; CHECK `ActorKind = 'Staff'` ⇔ not null), `Action`, `EntityKind`, `EntityKey varchar(80)` (a canonical lower-case GUID, or a fixed token for a singleton such as the Blog settings), `TitleSnapshot varchar(200)`, `ItemCount int NOT NULL DEFAULT 1` (CHECK ≥ 1), `CorrelationId uuid NULL`, `OccurredAtUtc`. **No foreign key to any content table and no cascade on an object**: deleting a post, a subscription or a bar cannot remove its activity.
- **Counters**: `MenuActivityStreams` is reused unchanged. Sequences are **per menu**, never global. PR-2 seeds one counter row (`LastSequence = 0`) for each new menu key; a key with no counter row is refused by the recorder (the existing "must not commit what cannot be counted" rule). The `newsletter` row already exists and is not re-seeded.
- **Cursors** (all additive; `StaffMenuSeen` is unchanged):
  - `StaffMenuSeen` keeps serving the **global** menus.
  - `StaffMenuPropertySeen(StaffAccountId, MenuKey, PropertyId, LastSeenSequence, UpdatedAtUtc)`, primary key the first three columns, for `promotions`. A per-Property cursor cannot be added to `StaffMenuSeen`'s key, so it is a separate table.
  - `StaffEntitySeen(StaffAccountId, PropertyId, EntityKind, EntityKey, LastSeenSequence, UpdatedAtUtc)` for **Calendar only**.
  - Every cursor only moves up (`GREATEST`), is never read from or written for another Staff id, and a Staff with no row counts from the baseline of decision D2 (account creation).
- **Watermarks** are the stream's `Sequence`, a `bigint`, and travel as **decimal strings** (validated as `^(0|[1-9][0-9]*)$`, like today); a JavaScript client compares them as `BigInt`, never as `Number`, never by time.
- **Numbers and the count**: the recorder takes the next number with `UPDATE "MenuActivityStreams" … RETURNING` **inside the business transaction** and keeps the row locked to COMMIT; the insert is in the same transaction, so a rollback leaves neither the number nor the activity. The unseen number is a **count of logical events over the physical rows left after filtering** for the Staff's permission and scope, the actor (not the Staff's own events), the baseline of decision D2 and the cursor (`Sequence > cursor`); outside Calendar it counts distinct `COALESCE(CorrelationId, Id)`, so two rows of one valid Save-then-Publish chain are one event and independent operations stay separate even on one object (§D). Calendar counts distinct unread objects instead. It is **never `current − lastSeen`**: gaps already exist (the Newsletter cascade removed rows) and must stay harmless. The table stays append-only; sequences are never edited.
- **Recorder**: an explicit `IAdminActivityRecorder` in Application, implemented in Infrastructure beside `NewsletterActivityLog`. A write service calls it **by name** at the end of its own transaction, after its business writes and its audit row, as the **last statement before COMMIT** and the last lock it takes. It requires an open transaction and throws without one (an autocommit insert would lose the atomicity). **No middleware or filter records activity**: only the service knows the object, its safe title and whether the operation really committed. If `EnableRetryOnFailure` is ever turned on, every caller must run the transaction inside the execution strategy, as any `BeginTransaction` already needs.
- **Audit and activity are different records**: `BlogAudits`, `RoomOccupancySegmentAudits` and the other audits are the business trail; `AdminActivities` feeds badges and history. Both are written in the same transaction, neither is derived from or repairs the other.
- **Actor** comes only from the verified Staff session (`ActorStaffId` of the authenticated principal); no request field can name it. Events that no Staff caused (the guest who verifies a Newsletter subscription, a system job) are `Public`/`System` with a null Staff id and **count for every Staff**; no fake Staff is invented, including for history that already exists.
- **Safe snapshots**: the caller composes `TitleSnapshot` from a short allow-list per menu (post title, category name, picture title, banner title, language name, currency code, menu label, network name, promotion name, property or room-type name; Calendar: room label and dates; bulk upload: `ItemCount`). It never contains guest names, e-mail, phone, notes or reservation codes, and never a secret. Newsletter snapshots carry no address ("a subscription"); the sender settings record a generic notice only. The text is trimmed, control characters removed, capped at 200, and rendered as text, never HTML.
- **Indexes** (proposed): `(MenuKey, PropertyId, Sequence)` for count and list; `(MenuKey, EntityKind, EntityKey, Sequence)` for grouping and Calendar; a partial unique index `(MenuKey, CorrelationId, Action) WHERE CorrelationId IS NOT NULL` as a backstop (§D).

### B. Proposed HTTP contract (none of it exists yet)

**Prefix.** The source does not support `/api/admin/v1/website` for all menus (item 2 above), and a `website` path implies the website permission. The shared routes use **`/api/admin/v1/menu-unseen`** (and `/api/admin/v1/activity`). This is a technical choice, not an Owner decision. The existing `/api/admin/v1/website/menu-unseen` routes stay **unchanged** (same shape, same `WebsiteSettingsManage` boundary) until PR-14 removes them, after an Admin build that no longer calls them has been deployed. Until PR-14 the new routes serve `newsletter` from the legacy tables (same entry shape), so one provider can read everything.

**Boundary.** A new marker `StaffSessionAttribute` (proposed, PR-3) opens a route in `Staff` mode with HTTPS only, a valid Staff session (else 401) and the request boundary (Origin 403, JSON 415 on a write), `no-store`, and **no permission**; permission is decided in the service per menu, from the database, on every request (no cache, nothing from the cookie). `StaffCalendarModeGuard.IsOpenInStaffMode` learns this marker explicitly, never a prefix. In `LocalGate` the routes are closed (404) and the Calendar shows no badge.

| Route | Purpose |
| --- | --- |
| `GET /api/admin/v1/menu-unseen` | `{ menus: { "<key>": entry } }`. Global entry: `{ count, lastSeenWatermark, currentWatermark }`. Property-scoped entry (`promotions`, `calendar`): `{ count, byProperty: [{ propertyId, count, lastSeenWatermark, currentWatermark }] }` where `count` is the sum of `byProperty`. A menu or Property the Staff may not read is **absent**, never shown as 0. `newsletter` is a top-level key of `menus`, present only when permitted. One statement, one snapshot; never writes. |
| `GET /api/admin/v1/menu-unseen/{menu}/changes?propertyId=` | The unseen list: at most 50 **groups**, `hasMore`, `unseenEvents` (exact count of logical events, or of unread objects for `calendar`, after the same filters as the badge, same snapshot), `lastSeenWatermark`, `snapshotWatermark`, and the scope (`menu`, `propertyId`). Never writes: opening or viewing the list sends no mutation. For ordinary menus the popover never acknowledges, and `snapshotWatermark` is informational (the popover is not a menu page load). For `calendar`, each item also carries `entityKind`, `entityId`, `presence` (`OnBoard` or `Removed`) and `observedWatermark`; only a `Removed` item has a "mark seen" action (decision D1). |
| `POST /api/admin/v1/menu-unseen/{menu}/seen` | `{ viewWatermark: "<decimal string>", propertyId? }` → atomic upsert with `GREATEST`; never moves back; **never acknowledges a newer mark on its own**. 200 returns the entry after the move. |
| `GET /api/admin/v1/activity?menu=&propertyId=&actorStaffId=&from=&to=&limit=&cursor=` | History, newest first. |
| `POST /api/admin/v1/menu-unseen/calendar/entities/seen` | `{ propertyId, entityKind, entityId, observedWatermark }` for one Calendar object: sent by a click on its bar (watermark from the board read) or by the "mark seen" button of a `Removed` item (watermark from that list), and it acknowledges exactly that Property, that object and that watermark. An `entityId` with **no activity row in that menu and Property** is 404 (same answer as an unknown menu), so a cursor can never be written for an object outside the Property of the Staff's membership. |

Rules shared by the routes:

- **Errors**: no session → 401; a menu that is unknown **or that the Staff may not read** → 404 `menu-unseen-unknown-menu` (anti-disclosure: the two look the same); a Property of a Property-scoped menu where the Staff has no membership → 404 as well; watermark not a plain non-negative integer, or above the menu's counter, or a malformed `limit`/`cursor` → 400 (`menu-unseen-watermark-invalid` stays); `propertyId` missing for a Property-scoped menu or present for a global one → 400. A refused watermark is never clamped to "everything so far". `POST /api/admin/v1/menu-unseen/calendar/seen` (the menu-level route) answers 400 `menu-unseen-use-entity-seen`: opening the page never acknowledges the board.
- **StaffId** is always the authenticated one; no request names another member.
- **A watermark belongs to the data it came with.** Every list a menu page loads must return `viewWatermark` from the **same snapshot** as its rows (the Newsletter precedent: REPEATABLE READ or one statement), and the page acknowledges that value unchanged. A watermark taken from an independent query made later and applied to older data would acknowledge events the Staff never saw. A page that loads several endpoints acknowledges the **minimum** of their watermarks. Those list-endpoint changes belong to the backend PRs (6, 8, 10, 11, 12), not to this ADR's PR. Acknowledging means "the menu page loaded", not "every object was displayed" (filters and paging are the screen's business).
- **History** needs one menu per query (`menu` is required): sequences are per menu, so a cross-menu list cannot be ordered by sequence. Order is `Sequence` descending; the cursor is opaque, carries the menu and Property and the last `Sequence`, and a cursor presented with different filters is a 400. Date and actor filters are `WHERE`, never ordering. History shows every event including the Staff's own (only the badge excludes own events), under the same read permission as the menu.

"Read" is the permission that opens the menu's own page and is also the permission for its count, unseen list, history and acknowledgement.

- The global Website and Blog permissions are not Property permissions, and a Property role never grants them (ADR 0008, ADR 0010). A Manager of one Property gets no Blog or Website number from being a Manager.
- **Filter on the server, before everything else.** The set of permitted menus and Properties is computed from the database per request (`HasGlobalPermissionAsync`, memberships), and the single SQL applies it, together with the D2 baseline, **before** `COUNT`, `LIMIT`, `GROUP BY`, the cursor, the sums and the totals, identically for the badge, the unseen list and Calendar's unread state. A Property or menu the Staff may not read contributes neither a number nor a title.
- Example: Manager at Property A and FrontDesk at Property B → `promotions` counts A only; `calendar` counts A + B.
- **Switching Property in the UI.** The sidebar number of a Property-scoped menu is the sum over **every Property the Staff may read**, and `byProperty` feeds a per-Property count beside the Property selector. An acknowledgement is **per Property**: opening Property A acknowledges only A's cursor with the watermark A's list returned, so unseen events of Property B stay unseen. The number shown is exactly what the cursors leave unseen.
- **Session changes.** The provider is keyed by Staff id; a new identity, sign-out or unmount starts a new generation and drops everything on the wire (the existing rule). A lost permission removes the menu from the next `GET` and the sidebar renders only the keys present, so the previous Staff's state is never shown to the next one; a 401 ends the session as every other 401 does.

### D. Correlation, grouping, consistency

- **Append-only.** An event row is **never updated in place**. Publishing inserts its **own** row with a **new** sequence and the same `CorrelationId` as the save it follows. Updating the saved row without a new number would let a Staff who acknowledged the draft at sequence 10 miss the publish; bumping the old row's number would reorder history and move rows between pages. Append-only keeps sequences immutable and keyset pages stable.
- **Physical rows versus logical events.** The table holds physical rows; the badge counts logical events. Outside Calendar the count is `COUNT(DISTINCT COALESCE(CorrelationId, Id))` over the rows left **after** filtering for the Staff, scope, D2 baseline, actor (other people's rows only) and cursor. Independent operations carry no shared id, so they stay separate, even on one object. Examples: a Staff who has seen neither the save nor the publish of one chain counts **1** (rows 10 and 12 share one `CorrelationId`); a Staff who acknowledged the save (10) and then receives the publish (12) has **1** unseen (only row 12 survives the cursor filter); five independent saves count **5**. Calendar is not counted by events but by `COUNT(DISTINCT object)` (below). The old Newsletter `count(*)` is correct for its own history and is not rewritten as if it had correlation.
- **Where the id comes from**: the browser generates one `uuid` per click that starts a chain and sends it on **every** request of that chain as the optional header `X-Admin-Correlation-Id` (a header, so no Blog body contract changes; the credentialed Admin CORS policy must list it in its allowed headers, a PR-6 task). Create-then-publish of a new post is the same chain and merges too.
- **When rows merge.** Three parts, decided by the recorder **after** it took the counter row (so two requests carrying the same id are serialised):
  1. A row whose `CorrelationId` has not been used in that menu yet **starts a chain** and keeps the id, but only for `Created` or `DraftSaved`.
  2. A `Published` row keeps the id only if it matches the chain's start row: **same actor, same entity**, and that earlier action is `Created` or `DraftSaved`.
  3. Every other case stores `CorrelationId = NULL` (the row is then counted on its own), including a second `DraftSaved` or a second `Published` with the same id. The business operation never fails because of it, and the partial unique index above holds by construction and is only a backstop. Reusing an id can therefore never merge unrelated rows. `CorrelationId` only links activity for shared display and counting. It replaces neither of two other mechanisms: **`expectedVersion` is optimistic concurrency** (it detects a stale write, and where an endpoint uses it a stale request is refused with its 409 before the recorder is reached), and **idempotency** (handling the same request again) is a business contract that exists only on the endpoints that implement it. This ADR does not claim every endpoint is idempotent, adds no such mechanism and changes no retry or 409 behaviour.
- **Failed publish**: the save committed in its own transaction, so its row stays; the failed publish wrote nothing.
- **The limit of 50 applies to groups** (actor + object), ordered by each group's newest sequence, fetched as 51 to decide `hasMore`. A group is never cut. The badge counts **logical events**; the list shows **groups**, each with its logical-event count (rows merged by correlation count once, the same number the badge uses), so the groups' counts add up to `unseenEvents` unless `hasMore`; when it is true, `unseenEvents` is returned as the total and the sum of the visible groups is never presented as that total. For `calendar` the list groups by object only (several actors listed).
- **Calendar objects.** The identity of a bar is the **object**, not the segment: `ReservationUnitId` (kind `reservation-unit`, covers assigned and unassigned ranges) or `RoomBlockId` (kind `room-block`), because moves and splits create new segment ids. All segments of one unit are one object. Consequences: several mutations of one bar are one unread object; an object that was split or moved keeps its read state; clicking any segment of a split unit acknowledges the unit.
- **What leaves the board.** Today's Calendar routes are assignment create, move, unassign and split-move, and block create, cancel and move; **no Calendar delete route exists**. An **unassign** moves the object to the unassigned lane, where it stays on the board and clickable, so it has not vanished. Only a **cancel** (a block, or a reservation) removes the bar; decision D1 covers it.
- **Calendar read state.** The existing board read (additive change, PR-12) returns per object `activity: { unread, watermark }` computed in the **same snapshot** as the board. Clicking a bar sends that bar's `watermark` as `observedWatermark`; the cursor moves up to it with `GREATEST`, refused above the counter, so a change that arrives after the snapshot has a higher sequence and stays unread. The count is `COUNT(DISTINCT object)` with another person's event above that object's own cursor and at or after the D2 baseline, the same filters as the unseen list. A Calendar snapshot holds a room label and dates, never a guest name. Objects that have left the board are not lost: the unseen list keeps them as `Removed` items (decision D1) with their safe snapshot and their own `observedWatermark`.
- **Lock order and contention.** The recorder is last. In Calendar writes it takes the `calendar` counter after the existing advisory locks and row locks (`AdvisoryLockCoordinator`); the counter row is then a serialisation point **across Properties**, held only for the tail of the transaction. This is accepted for now and measured in PR-12; the escape hatch is one counter row per Property, which the per-Property cursors already tolerate. It needs a scope column or a wider key on `MenuActivityStreams` (`MenuKey` is `varchar(40)` today), so it is a migration, not a naming trick.

### E. Rollout, realtime, compatibility

- **SignalR is only a hint** to refetch; the API is the source of every number. Polling and reconnect catch-up stay (30 s while visible, on focus, after reconnect). The hint is sent **after COMMIT**, carries only `{ menuKey, propertyId? }` (no title, no count, no actor), and the broadcaster re-authorises every connection for that menu or Property at every send, as `NewsletterLiveBroadcaster` does. The Newsletter hub keeps its own message until PR-14. Connections are in-process: with several API instances a hint reaches only the connections on the instance that committed, and polling makes up the rest; this is recorded as a limit and **no Redis backplane or outbox is built here**.
- **Registry and provider.** One Admin registry holds, per menu key, the label, path, scope and badge flag, and one provider reads `GET menu-unseen`. Adding a registry row does not create a recorder or a backend permission: each menu still needs its explicit recorder call and its permission check.
- **Sidebar**: a parent shows the **sum of the real numbers** of the children the Staff may see, formatted to `99+` only after summing; the entry keeps the real number in its accessible label (today the parent shows a dot, which the number replaces). Blog items are children of Website; Catalog, Promotions and Calendar are top level.
- **Migrations** are additive, each `Down` refuses while any activity, cursor or moved counter exists (as migration 25's does). Deploy order is database → API → Admin, and every PR leaves the application running.
- **Newsletter cutover (PR-14, last).**
  - Semantics change: today a deleted subscription removes its count; afterwards the event stays counted until seen (rule 3). Record it in the PR.
  - The `newsletter` counter row is reused and rows are copied **with their existing `Sequence`**, so there is no rewind or collision and every existing cursor stays valid. Neither side rewrites a number: after the cutover the next event takes the next number of that same row.
  - **Until the cutover the legacy tables are the only source of truth for the Newsletter.** PR-14 does **not** dual-write and does **not** copy a row that the legacy side can still delete into `AdminActivities` before the cutover: a legacy row disappears when its subscription is deleted (`NewsletterVerificationActivities.SubscriptionId` cascades), and a copy made earlier would keep a count the legacy number no longer has. Preparing data early to shorten the switch is allowed **only** in a separate staging area that no badge, list or cursor reads and that the cutover never trusts: the copy is always re-derived from the legacy set read under the boundary below, and staging serves only to reconcile counts beforehand (a dry run). Legacy rows have no Staff actor and become `ActorKind = 'Public'`; `ActorStaffId` is null, `Action` is `verified`, `TitleSnapshot` is the generic "a subscription" and `OccurredAtUtc` is kept. **History deleted by the old cascade cannot be recovered and no actor is guessed**; only rows that still exist at the boundary are copied. This is a stated limit, not a promise to rebuild history.
  - **The write boundary at the cutover.** Everything that can create or delete a legacy activity row must be stopped by the same boundary. Today, searching the whole `Back_End/src` for inserts, deletes, `TRUNCATE` and EF removes of these two tables (the Content Pack only classifies them as operational history and never writes them), that is exactly (a) `NewsletterActivityLog.RecordVerifiedAsync`, an `INSERT` into `NewsletterVerificationActivities`, and (b) `NewsletterSubscriptionAdminService.DeleteAsync`, whose `DELETE FROM "NewsletterSubscriptions"` removes the legacy rows through the cascade; manual operator SQL is not application code but is stopped by the same table lock. **Locking only the `newsletter` counter row is not enough**: `DeleteAsync` locks the subscription row and the mails and never touches the counter row, so a delete would interleave with a copy that waits only on the counter. The boundary is therefore taken on the legacy activity table itself, which both paths (and the cascade, and any binary that predates PR-14, with no cooperation from its code) must open for writing:
    - the cutover transaction first runs `LOCK TABLE "NewsletterVerificationActivities" IN SHARE ROW EXCLUSIVE MODE` under a `lock_timeout`. It waits for every legacy transaction that has already inserted or cascade-deleted (they hold a conflicting lock until their own COMMIT), and blocks every later one until the cutover commits or rolls back; plain reads are not blocked. On timeout the transaction rolls back and legacy stays the source; the command is run again later. Only then does it lock the `newsletter` counter row (lock order: legacy activity table, then counter row; no subscription lock is taken, so the write order subscription → mails → legacy activity table → counter row (see the lock-order invariant below) has no cycle with it);
    - **lock-order invariant (table before counter).** Every PR-14 write path that may need both the legacy-table lock and the `newsletter` counter row takes the legacy-table lock first and the counter row second, the same order as the cutover. This includes the verification recorder, which today takes the counter (`UPDATE … RETURNING`) before its `INSERT` into the legacy table: left in that order, a verification holding the counter and waiting for the table would deadlock with a cutover holding the table and waiting for the counter. If the implementation separates the statement that issues the sequence from the legacy write, it takes the table lock **before** issuing the sequence (for example `LOCK TABLE "NewsletterVerificationActivities" IN ROW EXCLUSIVE MODE`, which does not conflict with other legacy writers and does conflict with the cutover's mode). `DeleteAsync` already fits, because its cascade reaches the table before the recorder takes the counter as the last statement. This invariant does not change the atomic cutover above; the competing-verification case in acceptance group 1 verifies it;
    - a **fence** installed with the same migration and inert until the marker exists: an `INSERT` into `NewsletterVerificationActivities` fails (a trigger that raises when the marker row is present). A writer that decided "legacy" just before the commit and reaches the table after it therefore fails loudly and rolls back its whole transaction; the service re-runs that transaction once and decides again (now `AdminActivities`). No event is lost silently, and an old binary that is still running cannot keep counting in legacy mode; it gets an error until it is retired. A delete that reaches a legacy row after the cutover removes only the legacy copy and never touches `AdminActivities`;
    - **order of the rollout**: (1) database migration, additive (`AdminActivities`, the marker table, the fence, still inert); (2) API with the cutover-aware source switch, which reads and writes **legacy** while there is no marker; (3) **retire every instance and worker that runs an older API build** (including a background dispatcher that shares the build) and record the build in service per instance as evidence; (4) run the cutover command, once; (5) only now does any instance write `AdminActivities`; (6) the Admin build that calls the shared routes, and later the removal of the old routes. Steps 3 and 4 may not be swapped, and the command refuses to start while it cannot confirm step 3 (Owner or operator confirmation is an explicit input of the command). A Staff account is created only by the API's CLI; the command is not run while one is being created, so that "existed at the cutover" is not ambiguous.
  - **D2 compatibility at the cutover (one-time exception, Newsletter only).** D2 would drop a legacy Newsletter event whose `OccurredAtUtc` is before a Staff member's `CreatedAtUtc`, even though the legacy counter shows it unseen for that Staff (the legacy count starts at 0, with or without a cursor row). To keep the displayed number from changing merely because the source changes, a Staff member who **existed at the cutover** keeps every **still-existing legacy Newsletter event** that is above their old cursor, including one older than their account; a missing cursor row does not mean a new account. Their cursor is **not** raised or acknowledged to make the number smaller. A Staff member created **after** the cutover gets plain D2 and no backlog. New menus use D2 from the start; the exception exists only for the legacy Newsletter data.
  - **One transaction copies the boundary set and writes the marker.** After the table lock and the counter lock, in the same transaction: (a) if the marker row already exists, do nothing and report it (a retry after a commit finds it and neither re-imports nor moves it); (b) if `AdminActivities` already holds `newsletter` rows with no marker, abort and roll back (an inconsistent state is never merged); (c) copy **exactly the legacy rows that exist at that moment** into `AdminActivities` keeping each `Sequence`; (d) insert the marker once, `MenuActivityCutovers(MenuKey PK, LegacyMaxSequence, CutoverAtUtc)`, `ON CONFLICT DO NOTHING`, never updated, with `LegacyMaxSequence` = the counter's `LastSequence` read under the lock (not the highest surviving row: a deleted tail must not lower it) and `CutoverAtUtc` = read **after** the table lock is granted (not the transaction's start, which precedes the wait), from the same clock source that stamps `StaffAccounts.CreatedAtUtc`; (e) COMMIT. Any failure rolls the whole transaction back: no marker, no copied row, and legacy stays the only source read and written. The marker and the copy are visible together or not at all.
  - **Reads and writes choose their source from the marker, in the same snapshot.** The unseen read stays one statement (counter, cursor, count) and also reads the marker row in that statement, so it counts from the legacy table when no marker is visible and from `AdminActivities` when it is; because the copy and the marker commit together, one statement sees both or neither and never a marker with a missing copy or a copy with no marker. A write decides in its own transaction: the recorder reads the marker at its own position, the last statement before COMMIT (so a delete that waited on the cascade lock and finished after the cutover is still recorded in `AdminActivities`), and the fence above backs that decision. The Admin add, update and delete events that PR-14 introduces (`Staff` actor) are written **only once the marker is visible**: before it, those recorder calls write nothing, because the legacy table has no column for them and an `AdminActivities` row without a marker would make the cutover abort (step (b)). The `Staff` cursor semantics are unchanged: `Sequence > cursor`, cursors only move up, and the D2 exception below still applies. After the cutover, **deleting a subscription never deletes its history**: `AdminActivities` has no foreign key to the subscription, the cascade reaches only the legacy copy, and the already-imported verification record and its unseen state are left untouched (rule 3); the successful delete then appends exactly one `Staff` delete event under the existing Admin-delete rule (Product rule 8). A committed cutover is not reverted by this ADR; the legacy table stays for one more release for diagnosis: the fence forbids any new legacy insert after the cutover, while the cascade of a subscription delete can still clean the legacy copy and never touches `AdminActivities`.
  - **How the D2 exception reads the marker.** The two sets come from the marker, not from "now": a legacy event is a `newsletter` row with `Sequence ≤ LegacyMaxSequence`; a Staff member existed at the cutover when `StaffAccounts.CreatedAtUtc ≤ CutoverAtUtc`. For the Newsletter a row counts for a Staff member when `Sequence > cursor` and the actor is not that Staff member and (`OccurredAtUtc ≥ CreatedAtUtc`, or the row is legacy and the Staff member existed at the cutover). A missing cursor row never means "new account".
  - **What is and is not promised.** Preservation is judged on the same events and cursors at the boundary: for each existing Staff member, the number read from legacy just before the cutover equals the number read from `AdminActivities` just after it, at the same cursor. A new event, or a Staff member who really acknowledges, during the rollout may change a number legitimately; the ADR does not promise a number that never moves. The deleted-subscription rule is a separate, recorded semantic change that applies from the cutover on.
  - **PR-14 acceptance** (PostgreSQL integration evidence, not mocks; the three groups do not conflict):
    1. *A verification deleted before the cutover does not come back.* A verification is made and **staged**, then its subscription is deleted **before** the cutover (this proves staging is never an input of the copy). The legacy count immediately before the cutover and the shared count immediately after it are both **0** at the same cursor, and `AdminActivities` has no row for it. A delete that is still in flight when the cutover starts makes the cutover wait (or time out and roll back), and a verification or delete that starts while the cutover transaction runs blocks until it ends and then follows the new source (the fence turns a late legacy insert into an error and one retry). *Lock order:* a verification races the cutover in both interleavings: (i) the verification already holds the legacy-table lock (and, after it, the sequence) and has not yet written the legacy row, then the cutover starts and must wait for it; (ii) the cutover already holds the legacy-table lock, then the verification starts and must wait **on the table lock, before it issues any sequence** (the test observes this wait, for example in `pg_locks`). Both transactions end by COMMIT, never by `lock_timeout` (`55P03`) or deadlock (`40P01`), and the test sets `lock_timeout` above `deadlock_timeout` so that a real cycle cannot be hidden as a timeout. The verification in (ii) then follows the new source.
    2. *A verification that still exists at the cutover is copied exactly once, with its original `Sequence`.* A Staff member who existed keeps the unseen event, **with or without a cursor row**, including an event older than their account, and no cursor is raised. A Staff member created after the cutover follows D2 (only `OccurredAtUtc ≥ CreatedAtUtc`, no legacy backlog, even for legacy `Sequence` values).
    3. *After the cutover, deleting the subscription keeps the imported record and adds exactly one delete event.* At the same cursor, the delete leaves the already-imported verification row and its unseen state untouched, and the successful delete appends exactly one `Staff` delete event under the existing Admin-delete rule; the cascade removes only the legacy copy and no `AdminActivities` row. Isolated example: Staff B has `WebsiteSettingsManage`, existed at the cutover (or was created before the verification), is not the deleter, sits at a cursor below the verification, and no other unseen `newsletter` event lies above that cursor, so B's badge reads 1; Staff A deletes the subscription; B's badge reads 2 (the old verification and the new delete) and `AdminActivities` has grown by exactly one row. A subscription deleted **before** the cutover still reads 0 → 0 (group 1). *Retry and rollback never leave the marker and the data in different states:* a forced failure at any step leaves no marker and no copied row and legacy stays the read source; a second run after COMMIT finds the marker, imports nothing and does not change `LegacyMaxSequence` or `CutoverAtUtc`; a read during the run never sees a marker without its copy (or the reverse).
- **Risks, with no new infrastructure now**: contention on the per-menu counter (above), and permanent history growth. Measure rows per day and the unseen query plan when a menu goes live; retention stays an open Owner item.

## Decisions (Owner, 2026-11-20)

The two points the first draft left open are **Resolved**. They no longer block PR-3 or PR-12/13. The ADR as a whole stays `Proposed` until the Owner accepts this revised text.

- **D1 — Calendar objects that vanish (was OPEN-1; Owner chose (b)).** A cancelled block or reservation keeps an entry in the unread list, with its safe snapshot and a "mark seen" action for that one object.
  - Opening or viewing the list writes nothing. Clicking the badge only opens the list; it never acknowledges. This differs from ordinary menus only in that the list of **Calendar** may contain one explicit button; every other menu's popover has no mutation at all.
  - The button sends one `POST …/calendar/entities/seen` for exactly that Property, entity and `observedWatermark` (taken from the list snapshot), so a change that arrives after the snapshot has a higher sequence and stays unread.
  - A bar that is still on the board keeps being acknowledged by clicking it, under the contract in §D. Nothing is acknowledged automatically when an object is cancelled or disappears, and nothing expires by date in the first release. Acknowledging restores nothing and changes no business data.
- **D2 — Baseline of a Staff with no cursor (was OPEN-2; Owner chose (b)).** By default only events with `OccurredAtUtc ≥ StaffAccounts.CreatedAtUtc` count, on top of the menu's activation, the permission and scope, the actor and any existing cursor.
  - It is not the date a permission was granted or the date the page was first opened; `CreatedAtUtc` is never changed and no browser clock sets a baseline.
  - Cursors and watermarks stay sequence-based; the account date is only an extra condition, never a replacement for the sequence.
  - The same baseline applies to the badge, the unseen list and Calendar's unread state. The full history stays under the read permission: the baseline limits what is unread, not what is visible.
  - The Newsletter cutover is the one exception (§E): existing Staff keep their still-existing legacy unseen events.

## Consequences

- A Staff sees only numbers of menus and Properties they may read; the number counts logical events (physical rows filtered, then merged by a valid correlation) and is never a derived difference, and it survives a deleted object.
- A new Staff member starts with no backlog from before their account; only the Newsletter cutover keeps, once, the legacy unseen events of Staff who already existed.
- Activity rows accumulate forever; there is no retention job, no per-notification table and no new infrastructure.
- Every future menu costs one counter row, one registry row, one explicit recorder call and one permission mapping; none is automatic.
- Calendar needs three things the other menus do not: an object identity that survives moves, a per-object cursor, and a board read that reports its own watermark.
- The Newsletter keeps working unchanged until PR-14; its history lost to the old cascade stays lost.
