## 5. Why governance returns to a single repository checkout

The Owner observed that this session had been defaulting to creating a
second on-disk checkout (a linked worktree, `git worktree add`) for
backend implementation work, and asked why that was necessary when the
work could run directly in the existing repository checkout. On review,
`AGENTS.md`, `CLAUDE.md`, `docs/governance/RULES.md`, and
`docs/governance/WORKFLOW.md` all referred to "worktree" loosely enough
(sometimes meaning the checkout Claude writes in generically, sometimes
implying a dedicated `git worktree add` checkout) that a linked worktree
looked like the assumed default rather than an opt-in exception.

This closeout went through three iterations of that fix before landing on
the final rule, each triggered by a Codex `[P2]` finding on Draft PR #36:
first an explicit `WORKING_TREE_MODE`/`LINKED_WORKTREE` exception contract
with a full authorization-field checklist (§5.3), then a portable
(non-machine-path) definition of "primary working tree" (Correction C2),
then an optional-with-safe-defaults field design with a six-row policy
matrix to resolve a self-contradiction between "required minimum content"
and "defaults when omitted" (Correction C3). Before this branch was
reviewed again, Owner decided the entire exception mechanism was
unnecessary complexity for a single-agent, single-checkout workflow and
authorized Correction C4: remove the linked-worktree mechanism outright
rather than continue refining its authorization contract. The C3
optional-field/policy-matrix design is superseded by this decision and no
longer appears in any governance file — this worklog is the historical
record of that design, not a description of current policy.

Final rule (`docs/governance/RULES.md` §5, canonical; `AGENTS.md` §8,
`CLAUDE.md`, and `WORKFLOW.md` §8 summarize and point to it): each work
item has exactly one **active execution checkout** — the repository
checkout the Master Execution Prompt's `REPOSITORY` field designates. A
feature branch is checked out and worked on directly there. `git worktree
add`, creating an additional execution checkout, or switching to/using a
linked worktree to execute a work item are all prohibited — no exception,
no authorization field, no policy matrix. This is a rule about which
checkout is *actively used to execute* a work item, not a claim that only
one checkout may physically exist on disk: old, inactive, unrelated
worktrees (for example, from discontinued tooling — see §2 above) may
still exist and do not by themselves violate this rule or fail preflight;
if one is found, Claude audits and leaves it alone unless Owner gives a
specific instruction for that exact checkout. No fixed role changed —
Claude still writes, Codex still reviews read-only, and this rule does not
grant write access to Codex, a subagent, or a parallel implementation.
