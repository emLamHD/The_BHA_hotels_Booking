## 5. Why governance returns to a single primary working tree

The Owner observed that this session had been defaulting to creating a
second on-disk checkout (a linked worktree, `git worktree add`) for
backend implementation work, and asked why that was necessary when the
work could run directly in the primary repository checkout. On review,
`AGENTS.md`, `CLAUDE.md`, `docs/governance/RULES.md`, and
`docs/governance/WORKFLOW.md` all referred to "worktree" loosely enough
(sometimes meaning the checkout Claude writes in generically, sometimes
implying a dedicated `git worktree add` checkout) that a linked worktree
looked like the assumed default rather than an opt-in exception. This
closeout fixes that: all four files now state a single canonical default —
exactly one primary working tree per execution, with a feature branch
checked out directly in it — and gate any linked worktree behind an
explicit, fully-specified Master Execution Prompt exception (`RULES.md`
§5.3: path, isolation/parallel-execution reason, branch ownership, review
invocation location, cleanup owner, cleanup sequence). `RULES.md` §5 is the
canonical source for this; `AGENTS.md` §8 and `WORKFLOW.md` §8 summarize
and point to it, following the same canonical-source pattern already used
for the Graphify invocation policy. No fixed role changed — Claude still
writes, Codex still reviews read-only, and this default does not grant
write access to Codex, a subagent, or a parallel implementation.
