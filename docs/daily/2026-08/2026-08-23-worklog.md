## 4. Phase 1 — normalized domain and PostgreSQL cutover

- New Domain types: `InventoryHold`, `InventoryHoldItem`,
  `InventoryHoldItemNight`, `ReservationUnit`, `ReservationUnitNight`,
  `ReservationUnitPlan`, `CommitmentStatus`, `NightlyCommitmentSnapshot`
  (replacing `BookingHold`, `BookingHoldNight`, `BookingNightSnapshot`,
  `ReservationNight`); `Reservation.cs` and `BookingGuard.cs` rewritten for
  the Item/Unit shape. `BookingHoldStatus`/`ReservationStatus` enum
  identifiers kept unchanged (wire format is by member name, not type name)
  to avoid touching `Application/Bookings` DTOs unnecessarily.
- New EF configurations for all five normalized entities, each
  property-scoped via a `(PropertyId, Id)` alternate key +
  `(PropertyId, <FK column>)` composite foreign key — mirroring the
  discipline BE-003 already used for RoomType/RatePlan — so cross-property
  Item/Unit/Night/RoomType/RatePlan references are PostgreSQL-rejected, not
  just application-checked.
- Migration 7 (`CommercialCommitmentV2Foundation`) scaffolded via
  `dotnet ef migrations add` (so constraint/index names are guaranteed
  model-consistent, including three PostgreSQL-truncated composite FK
  names), then hand-edited to splice in: an expand phase (five new tables),
  a transform phase (deterministic MD5-derived-UUID backfill of every
  legacy Hold/Reservation row into `Q` Items/Units per the legacy
  `Rooms` count, ordinal-paired 1:1 between a Reservation's Units and its
  source Hold's Items), a fail-fast validation `DO $$` block (counts,
  duplicate-id, source-mapping, totals, Property-consistency checks) before
  any contract step runs, and a contract phase (repoint `Reservations` at
  `InventoryHolds`, drop legacy columns/tables). No PostgreSQL extension was
  installed; the deterministic-UUID helper is a `pg_temp` SQL function.
  `Down()` is a guarded reverse transform that verifies every Hold/
  Reservation's Items/Units still share one RoomType and one RatePlan per
  date before reconstructing the legacy shape, and fails before dropping
  any normalized row otherwise.
- Verified directly against a real PostgreSQL 17 database: fresh-database
  apply of all seven migrations; a migration-6 database seeded with
  representative Active/expired/multi-room/Confirmed/Cancelled legacy rows
  upgrading to migration 7 with exact Item/Unit/night counts, preserved
  totals, and correct `CommitmentStatus` mapping; the guarded downgrade
  reconstructing the original legacy rows byte-for-byte; and the downgrade
  guard raising (and preserving all normalized data) when a Hold's Items
  were artificially forced to span two RoomTypes. `dotnet ef migrations
  has-pending-model-changes` reports clean.

## 5. Phase 2 — commercial behavior cutover

Rewrote the six Infrastructure stores
(`BookingHoldCreationStore`/`ConfirmationStore`/`ReadStore`/
`CancellationStore`, `ReservationReadStore`/`CancellationStore`) and
`AvailabilityDataSource` against the normalized authority: creation
normalizes a `rooms = Q` request into `Q` Items sharing one nightly plan;
confirmation maps each Item to one Unit 1:1 via `InventoryHold.Confirm`
(unchanged idempotency/coherence-replay discipline, adapted to Item/Unit
comparison); availability and creation-time committed-demand queries filter
by `CommitmentStatus = Committed` / Hold `Active && unexpired`, counting
each normalized night-row exactly once; whole-Reservation cancellation
atomically transitions every still-`Committed` Unit. `BookingHoldDto`/
`ReservationDto` are now projected from the normalized rows (documented
invariant: every Item/Unit under one Hold/Reservation is identical in this
work item's scope, since only one RoomType/RatePlan line is ever
normalized) — the public JSON shape is byte-identical to before.
