## 3. Codex finding

`[P1] Reject cross-night rate-plan changes during downgrade` —
`CommercialCommitmentV2Foundation.cs:655-659`. The guard grouped by
`(InventoryHoldId, StayDate)` / `(ReservationId, StayDate)`, so it only
caught more than one `RatePlanId` on the *same* stay date, not different
`RatePlanId`s across *different* stay dates of the same Hold/Reservation.
The subsequent backfill selects one `RatePlanId` via `LIMIT 1`, so a
Hold/Reservation shaped that way would downgrade successfully while
silently discarding the RatePlan lineage of the unselected nights — the
opposite of the guard's documented intent.

## 4. Root cause confirmation (before any edit)

Read the full guarded `Down()` and confirmed: the normalized model allows a
distinct `RatePlanId` per `InventoryHoldItemNight`/`ReservationUnitNight`;
the legacy `BookingHolds`/`Reservations` tables carry only one
aggregate-level `RatePlanId` column; the existing guard's `GROUP BY`
included `StayDate`, so uniformity was checked per night, not per
aggregate; a Hold/Reservation with RatePlan A on night 1 and RatePlan B on
night 2 (uniform *within* each night) would pass that guard; the backfill
at lines 864-866 (Hold) and 892-894 (Reservation) then picks one
`RatePlanId` via `LIMIT 1` — confirming the lossy-conversion path Codex
identified.

## 5. Fix

Edited the existing seventh migration only (no eighth migration created;
`Up()` and migrations 1-6 untouched). Both `Down()` guards now
`GROUP BY InventoryHoldId` / `GROUP BY ReservationId` alone (dropping
`StayDate` from the `GROUP BY`), so `COUNT(DISTINCT RatePlanId)` is
evaluated across the entire Hold/Reservation aggregate before the
destructive backfill runs. Updated the guard's XML doc comment and the two
`RAISE EXCEPTION` messages to describe the corrected, aggregate-wide check
instead of the inaccurate "same stay date" framing.
