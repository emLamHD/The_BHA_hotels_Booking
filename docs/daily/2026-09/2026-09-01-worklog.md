### Phase 3 — real HTTPS + PostgreSQL + browser acceptance (commit `fbdea50` + manual pass)

Full detail in `docs/reports/PMS-CAL-001.1-completion.md` §5 — summary
here. A real Chrome browser (via the Claude-in-Chrome extension, not
connected at the start of this session — the Owner installed/logged into
it mid-session) drove the running Admin frontend against a running backend
over real HTTPS and a disposable PostgreSQL database
(`thebha_pmscal001_e2e`, dropped afterward), seeded with five concurrent
scenarios (fully-assigned, fully-unassigned, partially-assigned,
cross-RoomType, operational block) via a throwaway, uncommitted seed
fixture reusing the same direct-EF pattern already proven in the Phase 1
integration tests (there is no mutation HTTP API to create this data any
other way, by design).

Getting there required resolving, in order: no `sudo` TTY available to
either the Bash tool or the `!` interactive passthrough (Owner ran the
`libnss3-tools` install and later a full `mkcert -install` themselves, in
their own terminal); the discovery that Chrome's cert-warning bypass only
covers page navigation, not background `fetch()`, requiring a shared
`mkcert`-issued certificate for both the frontend's `dev:https` server and
a Kestrel override for the backend, trusted into Chrome's *system* store
(not NSS — confirmed Chrome on this Linux build does not read NSS for
TLS-root decisions) and a full Chrome restart. With the certificate
resolved, the frontend still failed — a genuine, previously-undetected
product bug: `GET /api/v1/properties` (reused by the Admin Property
selector) only carried the credentialed `customer-web` CORS policy, not
the Admin origin. Invisible to `curl` (no CORS enforcement) and to the
Vitest/RTL suite (`fetch` is mocked). Fixed with a third, uncredentialed,
`GET`-only CORS policy scoped to just that one action (commit `fbdea50`);
full backend suite re-verified with zero regressions before resuming.

Once resolved, all five scenarios, the property selector, range navigation
(including a genuinely empty range), filter toggling, both popover
variants, drag-immunity, and zero-console-errors were confirmed live in the
browser against real data; `psql` confirmed the database was untouched by
the interactive session (read-only invariant held under real use, not just
under test).
