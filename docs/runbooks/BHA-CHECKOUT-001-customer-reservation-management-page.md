# Runbook — Customer_Web reservation management page (BHA-CHECKOUT-001-PR09)

`/reservations/{id}/manage` in Customer_Web: the page behind the guest's e-mailed link (PR07) and behind the account owner's receipt button. It uses the PR06 API exactly as documented in `BHA-CHECKOUT-001-reservation-management.md`; **nothing in `Back_End/` changed except the four localization data files** (44 new text keys, see **Texts**). No schema, API, auth or cookie change.

## Who gets in

| Visitor | How | What the page does |
|---|---|---|
| Guest | The link in the confirmation e-mail: `https://<customer-web>/reservations/{id:D}/manage#<secret>` | Reads the secret from the fragment and removes it. **PR09-C8:** first a `GET …/manage` (no secret, the browser's cookies as they are); only `401 reservation.manage-session-invalid` lets the link be exchanged, once, with `POST …/manage/exchange`, and then the reservation is read with the session cookie. |
| Account owner | The **Quản lý đặt phòng / Manage booking / Gérer la réservation** button on `/paydone`, shown only for a **Direct** reservation, only while the verified customer session is the account that booked it | A clean link (no token). `GET …/manage` with the customer session; no exchange. A Hold receipt, a guest receipt and an unverified or different session get no button. Nothing attaches a guest reservation to an account. |
| Anyone else | — | One generic "this booking can't be opened from this browser or account" text (API 401/403/404 look the same), plus the support channel (PR09-C6: the public Website Social Settings, not the `/contact` template page). |

The reservation id is written once, **lowercase 36-character**, in the exchange, the read and the update (the session cookie's path follows the spelling of the exchange and browsers match cookie paths case-sensitively). An upper-case address in the browser is accepted and canonicalized; an id that is not a GUID asks for nothing.

## The link secret: what the page does and does not do

- The fragment is read once (`parseManageFragment`: exactly 43 base64url characters; anything else that is present is "malformed" and **nothing is sent**), then removed with `history.replaceState(history.state, …)` **and** `router.replace(…)`: the App Router keeps its own copy of the address and would write the secret back on every `router.refresh()` (a language switch). The entry keeps its router state.
- The secret lives only in the controller's memory until it is handed to the one exchange request; it is in no URL, state, storage, console line, thrown error or text. Checked in the browser: no request URL, `Referer`, console line, DOM, `localStorage`/`sessionStorage`, Customer_Web log or API log contained it.
- **One exchange per link-open** (PR09-C4: a link opened again **in the same tab** counts as a new open, see below). A new no-retry request path (`submitCsrfProtectedRequestOnce` in `lib/api/csrf.ts`) reads a CSRF token (a GET, repeated only for the token) and then sends the POST once. The shared `submitCsrfProtectedRequest` retries once after the exact antiforgery failure; it is not used for the exchange or for the arrival update. A module-level in-flight registry makes a re-mounted page join the exchange instead of sending another, and a read waits for it.
- **Same tab (PR09-C4):** a guest who pastes the e-mailed link into the tab that is already showing this page (typically after a 429 or a CSRF refusal) changes only the address fragment: the page stays mounted, so the effect that reads the fragment does not run again. The page now listens for `hashchange`; each such open removes the fragment at once (`history.replaceState` with the entry's own state, then `router.replace`, the same helper as on mount, so a later `router.refresh()` or language switch cannot write the secret back) and hands it to `controller.openLink`, which sends **at most one exchange for that open**: an open while an exchange of the view is already out is dropped (the service registry also joins an in-flight exchange of the id), an open while the identity is unverified waits for it, a malformed fragment sends nothing (`link-invalid`), an empty one does nothing. Rendering, `router.refresh()`, reloading the clean URL, a re-bind and **Try again** (a read) never send an exchange. Our own cleaning does not fire `hashchange`.
- **A guest link is read-checked before it is spent (PR09-C8).** A browser that still carries a customer cookie that no longer validates answers `/auth/me` with 401, so the session provider reports a *guest*; the API, however, answers `GET /manage` for that same cookie with `401 auth.session-invalid` and never treats it as a guest. Exchanging the link would then spend it for a booking that still cannot be read, and a clean browser could not use it afterwards. So, for a guest identity and a valid fragment, the controller first does the GET: **`reservation.manage-session-invalid`** (no management session) → exchange, once; **a readable booking** → shown, the link is left unspent; **`auth.session-invalid`** → 0 exchange POSTs, the CSRF token is not even requested, the secret is not kept for any retry, and the page tells the guest to open the original e-mail link in a private window or a clean browser (the fragment stays removed); **any other answer** (another 401, 403, 404, 429, network, 5xx, an unusable body) stops this open with its own text (`noAccess`, `linkRateLimited`, `linkNotSent`, config) and nothing is exchanged. The GET keeps the epoch check (a view that changed meanwhile sends nothing) and the exchange keeps the C5/C6 dispatch guard. Accounts keep their flow (no read before). **Limit:** the time between that GET and the POST is not covered by the client-side check; the server's own rules are unchanged.
- The exchange starts **automatically** when the page opens (that is the PR06/PR07 contract). Consequence: a mail scanner or preview tool that **executes JavaScript** would spend the link; a plain GET/prefetch of the HTML or RSC payload does not (verified: the link stays unspent). A spent link needs a new one; there is no resend feature in this release.

## What the guest is told

| Case | Text | Request behaviour |
|---|---|---|
| 401 (malformed, unknown, used, expired, another reservation's link) or a malformed fragment | `linkInvalid`: not valid / expired / used; reload if you already opened it here; otherwise contact the property | One POST (none for a malformed fragment); no read; no retry |
| 429 on the exchange, or the antiforgery 400, or the CSRF token unreadable | `linkRateLimited` / `linkNotSent`: **the link was not used up**, open it from the e-mail again shortly | One POST at most; never repeated by the page. The guest's own re-open (pasting the link again, same tab or new) is a new open with one more POST at most (PR09-C4) |
| Network error, 5xx, an unusable 2xx (outcome unknown) | `exchangeUncertain`: reload or press **Try again** to check the current session; if you still can't get in, contact the property | One POST; **Try again only reads** |
| Guest link, read before the exchange: 401 `auth.session-invalid` (an expired customer cookie) | `linkSessionExpired` (PR09-C8): the link was **not** used; open the original e-mail link in a private window or a clean browser | A GET; **0** POSTs; nothing retried |
| Read: 401 `reservation.manage-session-invalid`, 403, 404 | `noAccess` (generic, never says whether a booking exists; mentions contacting the property if the link was already used) | — |
| Read: 401 `auth.session-invalid` (customer cookie invalid) | "Your session has ended" + sign-in link (PR09-C8: and the same sign-in button of the `no-access` screen goes to `/login?returnTo=/reservations/<id>/manage`, so a successful sign-in comes back to this booking); one re-read of the customer session; **never treated as a guest**, no loop. PR09-C6: if the same signed-in account is verified again (e.g. signed in again in another tab) the view gets exactly **one** recovery read; a refusal of it ends the pass | — |
| Read: 429 / network / 5xx / unusable body | its own text and **Try again** (a read) | — |

## The view and identity changes

**Unsettled arrival updates (PR09-C4):** an arrival update whose result is pending or unknown keeps a *hold* keyed by `(reservation id, verified identity)` in the controller, separate from the per-view epoch. A session recheck (the identity goes through loading/unknown and the same account is verified again, e.g. after a failed sign-out) therefore does **not** reopen the form: the view comes back showing the *not confirmed* text with only "Check again". The hold stores an empty token and the key: no reservation data and no guest data. Only a definite answer **of that very request** frees it (200, 400/409/429, 401/403/404, or a token that was never read), even when it arrives while the view is hidden or after another identity or reservation was shown; such an answer publishes nothing, rebuilds no data and touches no other view's lock. A network error, 5xx or unusable answer keeps the hold. "Check again" then reads and opens the form **only if the hold is gone** (its own answer came); what the read shows never decides.

**Answers are checked where they are used (PR09-C5):** `read()` checks the epoch before it returns, and `load()`, "Check again" and the 409 re-read check it **again** when they continue, before any state or lock is touched, because the caller resumes in a later microtask in which the reservation or identity may already have changed. A POST that is still waiting for its CSRF token is handed to the transport only if the view that started it is still the current one: the controller passes `() => current(at)` through the service to the one-shot CSRF path, which asks it synchronously right before the hand-over, once the token of the current generation is in hand. A view that is gone sends **0** requests and the call fails with `RequestSupersededError`, distinct from a token failure (`CsrfTokenUnavailableError`) and from a request that was handed over (whose answer may be unknown). Both of the first two are *definite* (nothing was sent), so only **that operation's own hold** is released; nothing is shown in the new view and nothing is replayed. Changing the view never cancels a POST that was already handed over. A read that **began** while an arrival update of the view was unsettled cannot open the form even if the update's answer arrives first (that GET may predate the update's effect): the view shows *not confirmed* and only a successful read that began after the hold was gone, i.e. "Check again" once the update is settled, opens it.

A view belongs to `(reservation id, verified identity)`, where identity is `verifiedOwnerKey(session)` (`guest` / `customer:<id>`). While the session is loading or unknown nothing is requested and nothing private is shown. Any change of reservation or identity clears the data in the same call, aborts the read, and drops late answers (reads and arrival updates alike); the render also refuses state that belongs to another key, so no frame shows the old booking. A response for another reservation id is refused.

## Reservation details and estimated arrival

Shown from the PR06 DTO only: booking number, status, property (name and address of **the booked property**, looked up by `propertyId` in the whole public catalog the shared `StaySearchProvider` already loaded; no extra request; when it is not found the page shows "The BHA" with no address), stay dates and nights, guests/rooms, **pay at the property**, total, **collected** and **balance due**. `ledgerState = NotRecorded` shows "Chưa ghi nhận thanh toán" and no amount (nothing inferred). Guest name, e-mail, phone and room/plan ids are not kept.

**Decided (Owner/OC, PR09-C1):** for a **cancelled** booking the page shows its status, a cancelled notice, the total and the collected amount (when the folio is `Recorded`), but **not** the "balance due" line or the pay-at-property note. PR06 returns `balanceDueAmount` from the folio, and the folio does not post anything on cancellation, so a cancelled booking keeps its original positive balance in the API (shown by a real cancelled Direct booking: `Cancelled`, `Recorded`, total 2,000,000, collected 0, balance 2,000,000). Neither that balance nor a "0 ₫" would be a true statement of what is owed after a cancellation; that is the property's to say. Acceptance criterion for PR09 accordingly: the brief's "show the remaining amount" applies to **non-cancelled** bookings. Locked by `lib/reservationManagementMoney.test.ts`: Cancelled + Recorded (balance > 0) hides the balance line and the note in vi/en/fr; Confirmed + Recorded shows exactly the API balance; `NotRecorded` shows "Chưa ghi nhận thanh toán" and infers neither a collected nor a remaining amount (Confirmed and Cancelled). (The PR08 receipt of a cancelled replay is unchanged.)

Estimated arrival: the date list is the check-in day and the next day (UTC arithmetic on the text); the time is `<input type="time" step="60">`, sent as `yyyy-MM-dd` / `HH:mm` — the **property's wall clock**, labelled with `propertyTimeZoneId`; nothing goes through the browser's time zone (checked from a Los Angeles browser). The API decides the window, DST, status and permission. The form is disabled for a cancelled booking.

- Two clicks in the same tick send one request. Never replayed automatically (also not after an antiforgery refusal).
- **Known refusal** (400/429): its localized text, the form stays usable. A **409** (PR09-C2) shuts the form in the controller **and** the UI *before* the re-read starts, keeps the refusal text, and sends no second POST while the read is out. The read then decides: a still-editable booking opens the form again (refusal text kept); `Cancelled` stays shut by its status; a temporary read failure keeps writing shut and offers "Check again" (a read only); losing access clears the private view. A read that returns after the reservation or identity changed is dropped and neither opens nor shuts the new view's form.
- **Unknown result** (network, 5xx, unusable answer; PR09-C2, rule changed by PR09-C3): the server is **read first** and the read only refreshes the arrival shown. A read can never prove the earlier POST finished (the same value may have been stored before the request, and the lost POST may still be on its way), so it **never** says "saved" and never opens the form, whether it matches the submitted value or not. The state is always *not confirmed*: the submit lock holds for the rest of this page's life for that reservation and identity (PR09-C4: also through a session recheck), the text says the earlier request may still be applied, and "Check again" (a GET, never a POST) is the only action. A valid POST response still says "saved". The state "not saved" no longer exists.
- **Token could not be read** (`CsrfTokenUnavailableError`, PR09-C3): the POST never reached the transport, so nothing can be applied later. The page shows `customer.manage.eta.error.notSent` (vi/en/fr: not sent, nothing changed, press Save again), releases the lock, keeps the entered values, does **not** read to verify and does not resend; the visitor's own next Save sends one POST. Network errors after dispatch, 5xx, unusable answers, 400 antiforgery and 409 keep their own handling above.
- It changes no price, status, folio, night, unit, outbox event, delivery, inventory control, link or session (SQL snapshot before/after identical).

## Before enabling the e-mail link in an environment (Owner / operator; production configuration was **not** changed by this PR)

1. Deploy this build at the origin that will be `Booking:ConfirmationEmail:CustomerWebOrigin` (HTTPS only).
2. From outside, with that origin and a real reservation id: `curl -sI https://<origin>/reservations/<guid>/manage` must answer `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow` and a `Cache-Control` containing `private` and `no-store`. A CDN, proxy or hosting rule in front must not drop or rewrite them, and must not cache the page.
3. The API must be reachable from the browser over HTTPS (`NEXT_PUBLIC_API_BASE_URL` https, or the same-origin proxy `API_PROXY_ORIGIN`). If Customer_Web and the API are different **sites**, `Authentication:Cookie:SameSite` must be `None` (PR06); with the same-origin proxy the cookie is first-party and `Lax` is enough.
4. API `Cors:AllowedOrigins` includes that origin (credentialed). The exchange limit (`Booking:ReservationManagement:RateLimiting`, default 10 / 60 s per connection address) is per address: an office NAT or a shared proxy address shares one bucket. **With the same-origin proxy every guest's exchange reaches the API from the Next server's address**: unless that address is the configured trusted proxy (forwarded headers, `TrustedProxy` settings), all guests share one bucket of 10 exchanges per 60 s and the 429 text appears under moderate load. Configure that before enabling the proxy for this page (a real 429 through the proxy, from the Next server's single address, was verified in PR09-C1: the page shows the "link not used up" text after one exchange POST; the shared-bucket effect for many guests is not load-tested).
5. Click tracking is off at the mail provider (PR07 list) and the mailbox/scanner policy is understood (see the automatic-exchange note above).
6. The three switches of PR07 stay off until 1–5 are done.

## Known limitations

- A guest who opens the **same e-mail link a second time** (in a new tab, or pasted into the tab that already shows the booking, PR09-C4) in a browser that already holds the session sees the "link is not valid / already used — reload to check" text first; **reload** (the fragment is already gone) then shows the booking. The page does not try a read after a 401 exchange.
- The automatic exchange can be spent by a mail scanner that runs JavaScript.
- The submit lock lives in the page's controller (per reservation and verified identity, kept through a session recheck, PR09-C4): **reloading** the page during an unknown update result starts a fresh view that can submit again (the read on load shows what the server holds then; a lost POST that is still on its way can still be applied afterwards, and reload cannot tell). The PR09-C2/C3 guarantee is "no automatic or in-view replay", not a server-side idempotency key (the API has none for this endpoint; changing that is a contract change, out of scope).
- The hold is per verified identity: the same reservation opened by another identity (guest, then a signed-in account) is a different view and is not held by the first one's request. A server-side idempotency key would be needed for that, which is a contract change and out of scope.
- A change of reservation id while a request is in flight is covered by unit tests only (the browser covers logout and an account change in flight).
- **A session recheck while an exchange or an arrival POST waits for its CSRF token (PR09-C5):** the identity goes through loading and the same account is verified again, so the old operation's view is gone and it sends **0** requests. For a link exchange the new view's read then finds no session and shows the generic no-access text (the link was **not** spent); opening the link again works. For an arrival update its hold is released, but the re-verified view stays *not confirmed* until "Check again" (its read began while the update was unsettled); this is conservative, not a successful cancel.
- React StrictMode in development (mount, unmount, mount in one flush) is covered since PR09-C6: the controller starts its work one microtask after `bind()`, so the first, superseded binding consumes no link and sends nothing, and the second starts the exchange once. Verified with the real page under `<StrictMode>` in `lib/reservationManagementMount.test.ts` (react-dom/client on a minimal DOM shim); the production build has no double mount (browser run in the PR09-C6 section).
- **Floating contact buttons (observed in PR09-C7, not changed):** `FloatingContactActions` (outside PR09's files) reads the same endpoint with `fetch`'s default credentials, so in a same-origin deployment (the API proxy) its request does carry the customer's session cookie; in the browser run below it did. Setting `credentials: "omit"` there is a separate, out-of-scope change.
- **Guidance can be replaced (PR09-C8):** after the `linkSessionExpired` guidance, an identity recheck (an outside sign-in or sign-out) runs an automatic load; with the cookie still invalid it gets `auth.session-invalid` and shows the generic session-ended text instead. The page asks for no refresh on this path, so it happens only on such an outside change; the link stays unspent either way.
- **Support channel (PR09-C6):** the page reads the public settings once per mount (no retry, no polling); a change an admin saves shows on the next load. It is fixture-tested; it has **not** been checked against a deployed environment, and as long as no channel is enabled there the guest sees the notice instead of a button.
- `PayDoneReceipt` (`app/paydone/PayDoneReceipt.tsx`) has the same Riverside-only property lookup as the management page had; it is outside PR09's files and was **not** changed in C5.
- Daylight-saving behaviour is the API's (PR06 tests); not exercised in the browser (Asia/Ho_Chi_Minh has none).
- `Cache-Control` is Next's dynamic-page value, not the literal `private, no-store`.

## Not in PR09

Resend-link / new-link flow, cancellation or any other change from a management session, no-show or fee policy, deposits/cards/QR, linking a guest reservation to an account, Admin_Web, any Backend code/schema/API/auth/cookie change, a stored locale for the e-mail, a "My bookings" list, real provider sends.

**Removal and re-keying are applied at commit (PR09-C6):** the page disposes the controller in a *layout-effect* cleanup keyed on `(controller, reservation id, verified identity)`, so the dispatch guard (above) sees a removed or re-keyed view as gone in the commit itself. A passive-effect cleanup runs later, and a CSRF token that resolves in between would otherwise find the old view current and let a pending exchange or arrival update be handed to the transport after the visitor left. Starting stays in the passive `bind` effect and `bind()` defers `begin()` by one microtask, guarded by the epoch (see Known limitations for StrictMode). `dispose()` clears neither `writeHolds` nor the session-recovery marker.

**Session recovery (PR09-C6):** after `auth.session-invalid` the controller remembers `(reservation id, verified identity)` and asks for the session refresh once. When the identity goes through loading and the **same signed-in account** (`customer:<id>`) comes back, exactly one recovery read is allowed (the private view stays hidden while it is unverified; the link is not exchanged again). If that read is refused too, the error stays, the session is not refreshed again and no further read starts for that key. A guest view gets no recovery. A successful read, or another verified identity or reservation, resets the marker; the loading transition never does. A binding that was superseded before it started cannot use up the one recovery read. **The limit applies only to automatic starts (PR09-C7):** a link the visitor opens on purpose (a fragment pasted into the tab) is exchanged once whatever the marker says; once that exchange has succeeded, the read that follows it is marked as the used allowance and is never a reset, so a refusal of it ends the pass with no refresh and no loop (an exchange that fails leaves the allowance as it was, so the recovery read still happens when the account is verified again); a malformed fragment sends nothing and leaves the marker alone. The refresh the controller asks for does pass through the loading identity: `lib/customerSession.ts` `startRead()` publishes `LOADING_SESSION` before it reads `GET /auth/me` (and `requestRefresh` in the idle phase calls it), so the identity key goes to `null` and back and the page's `bind` effect re-runs. The tests drive that transition by hand (`bind(loading)`, then `bind(account)`); the real provider was **not** mounted in them.
