# Runbook — home hero pictures (CUST-WEB-HERO-001)

## Configure where uploaded pictures live

The API reads one setting: `WebsiteMedia:RootPath` (environment variable `WebsiteMedia__RootPath`). It must be a directory the API process can write, **outside the source tree and the build output**, on storage that survives a restart or redeploy (a mounted volume on a server, a container volume). Nothing is created in `Front_End/*/public`; no commit or rebuild is needed to see a new picture.

| Where | Value |
|---|---|
| Developer machine (local config only, not committed) | `export WebsiteMedia__RootPath=/home/admin1/bha-data/media` before `dotnet run`, or user-secrets `dotnet user-secrets set WebsiteMedia:RootPath /home/admin1/bha-data/media --project Back_End/src/TheBha.Api` |
| Tests | each integration-test factory (shared by the tests of its collection) gets its own temp directory (`bha-hero-media-<guid>` under the system temp path), deleted when the factory is disposed |
| Production (later) | the persistent data/volume path of that host; there is deliberately **no default** and no path in code, appsettings or the database |

If it is unset the API still starts: `POST …/hero/media` answers `409 hero-storage-not-configured`, the built-in pictures keep working, and a picture already recorded whose file is not there is answered `404` (the Customer shows the overlay and the search without it).

Files are `<RootPath>/hero/<32 hex>.<jpg|png|webp>`; the database holds only the relative key and metadata (`WebsiteHeroMedia`). **Back up the directory together with the database**: a saved slide whose file is missing cannot be published again (Save refuses it with `hero-media-missing`) and shows no picture.

## Admin proxy deployments

A deployed Admin proxies `/api/admin/v1/*` to the API (`API_PROXY_ORIGIN`, `BHA-ADMIN-PROXY-001`), plus the two public reads `/api/v1/website/config` and `/api/v1/properties` (`BHA-BLOG-001-CP03-C7`). The editor's thumbnails and preview therefore load from the Staff route `/api/admin/v1/website/hero/media/<id>` (Staff session, same-origin cookie), so no extra rewrite is needed. The Customer reads the public route `/api/v1/website/hero/media/<id>` on the API base it already uses (direct, or through its own `/api/*` proxy).

## What the application never does

It never deletes a recorded picture, never writes outside `hero/` under the root, never takes a path or a name from the client (the key is generated by the server), and never fetches a picture from a URL. Unused uploads accumulate (no garbage collection); remove a file by hand only after checking no slide refers to it (`SELECT * FROM "WebsiteHeroSlides" s JOIN "WebsiteHeroMedia" m ON m."Id" = s."MediaId"`).

## Restart check

Restart the API with the same `WebsiteMedia__RootPath` and request any uploaded picture's URL (`/api/v1/website/hero/media/<id>`): it is served byte for byte. The migration (13) seeds once and never again; a restart does not reseed or overwrite an edit.

## Apply the migration

`dotnet ef database update` (order 12 → 13). Rolling back (`Down`) removes the three hero tables and the hero's text rows; uploaded files on disk are left where they are.
