## C3 — sitemap capacity guard (OC decision after the review of C2; sitemap index DEFERRED; review of C3: NOT_RUN)
Base `bb9f7f279a15a5dbf121a2d226948dee399ff91f`, start `b5e38dbf6684cbc8fac1fd051794b47cca0b5d09`; final head in the PR. Customer_Web only; no backend, schema, dependency, route or registry change.
- **The Codex review of C2** (RUN on `b5e38db`) returned one P2: above 50,000 URLs the single `<urlset>` violates the sitemap protocol. OC judged it well-founded but **not a C2 regression and a sitemap index out of the agreed scope**, so it chose to **guard** the one-file sitemap and **defer the index**. **A sitemap index is NOT implemented.**
- **What changed (`sitemap.ts` only):** one file is valid, or the request fails with the existing "not available" HTTP 500 — never a 200 that is oversized, truncated or missing URLs. (1) At most **50,000 URL entries**, counted after de-duplication over the static pages, every language's Blog index, categories and posts; refused the moment the 50,001st would be added, before the rest is walked or any XML is built. `sitemapXml` refuses a longer list on its own too. (2) At most **52,428,800 bytes** of UTF-8 for the whole file — header, markup, escaping and the newlines between rows — measured with `Buffer.byteLength` as the rows are made (not `string.length`), so an oversized file is never joined. Inside both limits the URLs, `lastmod`, languages, headers and XML are exactly as before.
- **Tests (fixtures, no PostgreSQL):** `sitemap.test.ts` — 50,000 accepted / 50,001 refused (static pages, index, a category, two languages and de-duplication counted), exact 52,428,800-byte boundary accepted and +1 refused, `€` (3 bytes) and `&` (5 bytes as `&amp;`) counted as bytes, ordinary output unchanged; new `app/sitemap.xml/route.test.ts` through the real `GET` — ordinary list 200 `application/xml`, exactly 50,000 entries 200, 50,001 and an 18-URL / ~54 MB list → HTTP 500 `text/plain` "The sitemap is not available.", no `<urlset`, `no-store`, the logged reason names the limit. **Red on the `b5e38db` logic: 6 of the 8 new tests** (the other two — the ordinary route answer and the unchanged-output test — pass on both); green after.

## C4 — backslash in a Blog link (review of C3 on `bc3bd18`: RUN, CORRECTION_REQUIRED; review of C4: NOT_RUN)

- **Finding [P2]** (`Front_End/Customer_Web/src/lib/blog/body.ts`, `safeHref`): `/\evil.example` started with `/` but not `//`, so it was an "internal" link; a browser reads `\` as `/`, so `new URL("/\\evil.example", "https://site.test").origin` is `https://evil.example`. A defect of the original Customer work, not of the C3 sitemap guard (guard and limits unchanged; the sitemap index stays DEFERRED).
- **Root cause / fix:** `safeHref` never looked at `\`. It now returns `null` for any value containing a backslash (one condition, no rewriting of the link into another one). The API already refuses a backslash (`BlogLink.IsSafe`), so this makes the Customer rule match it; a stored body that nevertheless carries one is shown as plain text by the existing renderer path (text, bold/italic and the rest of the post kept, no anchor). Allowed forms unchanged: internal path with query/hash, `https://`; still refused: `//`, `http:`, `javascript:`/`data:`, control characters.
- **Red → green:** 3 new tests in `body.test.ts` (real backslash built with `String.fromCharCode(92)`, asserted as code 92; `new URL` proves the origin is external before the fix; no network). On `bc3bd18` 2 of 3 are red (`safeHref` accepts the four backslash inputs; the renderer emits `href="/\evil.example"` and `href="/offers\x"`), the URL-origin one passes by design; after the fix all pass.
- **Checks run (local):** `vitest src/lib/blog` 63/63; whole Customer `vitest` 81 files / 1448 tests; `npm run lint`; `tsc --noEmit`; `next build`; `git diff --check` — all pass.
