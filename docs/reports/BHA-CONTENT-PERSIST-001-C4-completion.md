| **F1** hero/menu texts | the edited-collection protection (C2) skipped the collection's own rows but not its `WebsiteTranslations` | a pack text whose key is a menu item (`content.menuItem.*`) or a hero one (`content.heroSlideshow.*`, `content.heroSlide.*`) is not added when the target's menu / hero was saved by staff and the target has the language (`IsProtectedCollectionText`; the parent state is the one read under the website lock). | **F2** ids in translation keys | foreign-key columns were re-pointed, `WebsiteTranslations.Key` was not | `RemapContentKey` rewrites the id of `content.<property\|roomType\|ratePlan\|amenity>.<id>.<field>` through the existing maps, before the row is looked up, inserted or verified (uses `ContentKey.TryParse/For`, the convention `ContentCatalog` generates) | **Before:** the text of a property the target holds under another id is not under the target's key (`Expected "C4 property", Actual null`) and the public dictionary does not show it, while verify passes. **After**, with target rows of the same slug/code under other ids for the property, a room type, a rate plan and an amenity: website group only, all four texts sit under the target's keys, `GetDictionaryAsync("en")` returns them, no row under a source id, the catalog is not written; a staff text already under the target's key is kept (public reader shows it) |
| **F3** Blog seed | the "source edit over an untouched default" rule was website-only | it now covers `BlogCategories`, `BlogCategoryTranslations`, `BlogCategorySlugs` and `BlogSettings`. **Signal:** a category is untouched when `Version = 1` and neither `CreatedByStaffId` nor `UpdatedByStaffId` is set (every `UpdateCategoryAsync` raises the version and records the author), read before any write; its texts and slugs follow it. Settings: the same signal on their own row. The take always runs the version-checked `UPDATE` of the category / settings row (the row is stamped with the source's version and the actor, so a Staff save that lands during the import becomes a CONFLICT and a rollback instead of being overwritten, and the target no longer looks untouched). Slugs go in "stops being current" first, so one current slug per language. A target whose staff edited the category keeps its texts and slug, and the pack's current slug for it is not added as a second one | **Before:** on a freshly migrated database the import of a pack with the renamed category fails: `CONFLICT: BlogCategorySlugs en/featured-places: 23505 UX_BlogCategorySlugs_Current`, nothing written, exit 4; with a target that renamed it too, the same. **After**, the source edited through `IAdminBlog` (rename the slug, add a category, make it the homepage's): dry-run, apply, verify and a second apply exit 0; the new slug is current and the old one history, `GetCategoryAsync` answers the new one and redirects the old (`RedirectSlug`), `HomeSectionAsync` returns the new homepage category; a target that renamed the slug and chose its own homepage category keeps both |

## 3. Limits that remain

- F1 protects a collection's texts for languages the target already has; a language the import adds receives the pack's texts even if the target's hero was saved.
- A category's texts and slugs are judged by the category's version; a category the staff created and never edited has an author and is therefore never treated as a seed.
- Where the target's staff renamed the category, the pack's slug history for it is only added when it does not make a second current slug; the old slugs of the pack are carried as history.
- `promotion` keys (`content.promotion.<id>.*`) are not re-pointed: the finding names four entities, and a pack offer mapped to the target's own offer is deliberately left out (C1), so its texts must not be written onto it. OC to decide if offers' texts need the same treatment.
