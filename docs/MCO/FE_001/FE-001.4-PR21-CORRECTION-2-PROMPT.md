## 2. Confirmed remaining defects

### P1 — Availability can bypass the Hold lock through a stale React render

`SectionAvailabilitySearch` currently derives `searchLocked` from the phase
captured by its latest React render. Its event handlers check that rendered
boolean, but `BookingHoldFlowController.submit()` sets its synchronous
`inFlight` guard before React necessarily commits a new render.

Therefore, if Create Hold submit and Availability submit occur in the same
tick, the Availability handler can still observe `searchLocked === false` and
call `runSearch()`.

This is not made safe by `resetSearchSelection()` becoming a reducer no-op:
`runSearch()` already performs independent side effects:

- aborting/replacing the current Availability request;
- incrementing request identity;
- changing local loading/query/error state;
- calling `searchAvailability()`.

The authoritative Hold coordinator must reject the Availability operation
**before any of those side effects occur**.

There are two related inconsistencies:

- `active-session` is not included in `searchLocked`, although the reducer,
  report, and document say a succeeded Hold locks new Availability searches;
- Property/date/guest/room inputs remain editable in locked phases.

### P2 — Contact PII and obsolete offer data remain after definitive success

In `bookingHoldFlowReducer`, `attempt-succeeded` currently spreads
`...state`, then clears only `attempt`, `fieldErrors`, and `errorMessage`.

As a result, the root provider continues retaining:

- `contact.fullName`;
- `contact.email`;
- `contact.phone`;
- the selected offer snapshot;
- the offer display label.

This contradicts the approved invariant and current documentation that, after
a definitive success, only the minimal active Hold session and retained
guest-access token remain.

## 3. Required correction

Implement the smallest coherent frontend correction. Preserve the current

### 3.1 Authoritative synchronous Availability gate

Add an API at the authoritative Booking Hold coordinator/provider boundary
that synchronously decides whether an explicit Availability operation may
begin.

The exact name is your choice, for example:

- `tryBeginAvailabilitySearch(...)`;
- `runAvailabilitySearchIfAllowed(...)`; or
- a similarly explicit guarded-operation API.

The behavioral contract is mandatory:

1. It must consult the coordinator's synchronous state, including its
   same-tick `inFlight` guard, rather than trusting a phase boolean supplied
   by a React render.
2. It must reject Availability search/retry in:
   - `submitting`;
   - `uncertain`;
   - `active-session`;
   - the same tick in which a fresh Hold submit or exact retry has already
     acquired the synchronous mutation lock.
3. Rejection must occur before all Availability side effects:
   - no request abort/replacement;
   - no request-ID increment;
   - no local search-state mutation;
   - no selection reset;
   - no `searchAvailability()` call.
4. On acceptance, the coordinator must synchronously invalidate the old
   Hold selection before the Availability request is allowed to start.
   A fresh Hold submit in the same tick after an accepted new search must
   not create a Hold from the now-obsolete offer.
5. Search and Hold creation must therefore serialize safely in **both**
   same-tick orders:
   - Hold submit/retry first, then Availability search: Availability is
     rejected and sends zero new requests;
   - Availability search first, then Hold submit: the old offer cannot
     produce a Hold, and zero Hold POSTs are sent until a new live offer is
     explicitly selected.
6. Do not implement this as a timing workaround, `setTimeout`, debounce,
   effect, or DOM-only disable. Do not depend on React re-render timing.
7. Preserve the existing Availability abort/request-identity behavior for
   two ordinary allowed searches.

It is acceptable to strengthen the controller's internal synchronous
serialization state or introduce a small React-free helper. Keep one
authoritative decision path. Do not duplicate business rules across unrelated
components.

Update every explicit Availability entry point to use the gate, including:

- normal form submit;
- Retry last search / Search again;
- any programmatic path that directly invokes the request runner.

`SectionAvailabilitySearch` must not start its local or network work until the
authoritative gate accepts the operation.

### 3.2 Locked UI consistency

For `submitting`, `uncertain`, and `active-session`:

- disable the Property selector;
- disable check-in/check-out inputs;
- disable adults/children/rooms inputs;
- disable Availability submit and retry-search controls;
- disable all offer-selection CTAs;
- keep the existing contact/submit restrictions appropriate to the phase.

Derive display/accessibility lock state from one shared phase predicate where
practical, but treat disabled styling only as UX. The synchronous coordinator
gate remains the behavioral authority.

Do not clear, replace, or hide the active session merely to make the search
form editable. Multiple active Holds remain out of scope.

### 3.3 Scrub PII and obsolete offer state on definitive success

Change the authoritative `attempt-succeeded` reducer transition so it
constructs the successful state deliberately instead of carrying sensitive
or obsolete fields through `...state`.

After an accepted definitive success:

- `phase` is `active-session`;
- `session` is the correctly merged current session/result;
- the same-Hold replay-null guest-token retention rule remains intact;
- `contact` is reset to empty values;
- `offer` is `null`;
- `offerLabel` is `null`;
- `attempt` is `null`;
- `fieldErrors` is `null`;
- `errorMessage` is `null`;
- only non-sensitive state actually required for stale-operation safety may
  remain.

Do not render, log, persist, or copy the cleared contact values, raw guest
token, idempotency key, CSRF token, or cookie into documentation or fixtures.

Scrubbing happens only on definitive success. An `uncertain` operation must
continue retaining the exact immutable body/key and contact data required for
manual exact retry. A known error may keep editable contact values.
