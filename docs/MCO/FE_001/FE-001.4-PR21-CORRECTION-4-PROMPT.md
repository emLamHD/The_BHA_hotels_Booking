## 2. Confirmed remaining defect

### P1 — Definitive-success scrubbing makes the success summary unreachable

The second correction correctly changed the reducer's `attempt-succeeded`
transition to scrub contact PII and obsolete offer state. Its intentional
post-success state includes:

- `phase === "active-session"`;
- `session !== null`;
- `offer === null`;
- `offerLabel === null`;
- empty contact fields;
- `attempt === null`.

However, `BookingHoldPanel.tsx` currently evaluates this guard first:

```ts
if (phase === "idle" || !offer) {
  return null;
}
```

The `active-session && session` success-summary branch appears only after that
guard. Therefore every valid scrubbed success state returns `null` before the
summary can render.

Actual customer impact:

- the server may successfully create or replay a Hold;
- the flow moves to `active-session` and locks further Availability/Hold
  actions correctly;
- the Booking Hold panel disappears;
- the customer cannot see the server-backed Hold ID, outcome, status, stay,
  amount, creation time, or expiry time.

CI remains green because current tests prove reducer scrubbing/session
retention but do not exercise the panel's production render ordering.
