## Current backend contracts

### CSRF token

Endpoint:

`GET /api/v1/auth/csrf`

Success:

`200 OK`

Body:

```json
{
  "token": "<opaque request token>",
  "headerName": "X-CSRF-TOKEN"
}
```

Behavior:

- the response stores the antiforgery secret in an HttpOnly cookie;
- JavaScript must never attempt to read that cookie;
- the returned request token must be sent using the returned `headerName`;
- the request and all subsequent unsafe requests use credentials;
- the token is identity-bound and may become invalid after an authentication
  transition or backend/Data Protection change;
- CT-CONTRACT-002 established one stable antiforgery-failure response:
  - status: `400`;
  - media type: `application/problem+json`;
  - title: `Invalid antiforgery token`;
  - detail: `A valid antiforgery token is required for this operation.`;
- the API formatter recognizes the framework's
  `IAntiforgeryValidationFailedResult` marker, not a status code, response
  body, or endpoint name;
- ordinary business-validation `400` responses remain distinct and must never
  be treated as antiforgery failures.

The generated OpenAPI document and live endpoint remain final authority for
JSON casing, required fields, and nullability.

### Create Hold

Endpoint:

`POST /api/v1/booking-holds`

Required headers:

- the header name and token returned by `GET /api/v1/auth/csrf`;
- `Idempotency-Key`.

Optional ambient credential:

- `.TheBha.Customer` HttpOnly cookie, managed only by the browser/backend.

Request body:

```text
propertyId
roomTypeId
ratePlanId
checkIn
checkOut
adults
children
rooms
fullName
email
phone
```

The client must never send any of these as authoritative request fields:

- price, nightly rate, total, or currency;
- inventory or available rooms;
- status;
- server time, created time, or expiry;
- customer account ID;
- guest access token or guest-token hash;
- idempotency hash or request fingerprint;
- PhysicalRoom or internal inventory-control data.

Success semantics:

- `201 Created` — a new Hold was created;
- `200 OK` — the same idempotency key and exact normalized request replayed an
  existing Hold;
- a new anonymous `201` returns a one-time `guestAccessToken`;
- an authenticated `201` returns `guestAccessToken: null`;
- a replay returns `guestAccessToken: null`;
- replay does not refresh expiry, price, or any Hold snapshot.

Current error semantics:

- `400` — malformed request, invalid contact data, invalid idempotency key, or
  invalid antiforgery token;
- `401` — an invalid ambient customer session;
- `404` — the Property/RoomType/RatePlan selection is no longer active or
  found;
- `409` — the same key was used for a different request, price coverage is
  incomplete, stop-sell applies, inventory is insufficient, or another
  current conflict prevents creation.

Errors use Problem Details.

### Create Hold request rules

- IDs must be non-empty live IDs.
- Stay range is half-open and requires `checkIn < checkOut`.
- Maximum stay is 30 nights.
- `adults >= 1`.
- `children >= 0`.
- `rooms` is between 1 and 10.
- `fullName` is trimmed, required, and at most 200 characters.
- `email` is trimmed, required, at most 256 characters, and matches the
  backend's simple contact-email rule.
- `phone` is trimmed, required, 7–32 characters, contains at least one ASCII
  digit, and contains only digits, spaces, `+`, `(`, `)`, `.`, or `-`.
- The server revalidates current selection, price, and inventory inside its
  transaction. A previously returned Availability offer is not a reservation.

The Hold begins as `Active`. The backend sets `expiresAtUtc` to exactly 15

## Security and recovery invariants

### CSRF

- Cache the request token and returned header name only in JavaScript memory.
- Deduplicate simultaneous first acquisition with one in-flight promise.
- Never store the token in `localStorage`, `sessionStorage`, IndexedDB, a
  cookie, a URL, DOM attributes, logs, analytics, or documentation.
- Never hard-code the CSRF header as the only authority; use `headerName`
  returned by the server.
- Caller-provided case variants must not produce duplicate CSRF headers.
- For the exact CT-CONTRACT-002 antiforgery Problem Details only—status `400`,
  title `Invalid antiforgery token`, and detail
  `A valid antiforgery token is required for this operation.`:
  1. invalidate the cached token;
  2. obtain a fresh token;
  3. retry the exact same unsafe request once.
- That retry must preserve the exact body and exact `Idempotency-Key`.
- Never retry more than once.
- Never treat an arbitrary `400` as an antiforgery failure.
- Never automatically retry `401`, `404`, `409`, `429`, `5xx`, cancellation,
  or a network/ambiguous transport failure.

### Idempotency

- Generate the key in the browser using cryptographically secure randomness,
  preferably `crypto.randomUUID()` with a short non-sensitive prefix if one is
  useful.
- Do not use `Math.random`, timestamps alone, contact data, or offer fields as
  the entropy source.
- The key is opaque, case-sensitive, and at most 256 UTF-8 bytes.
- The endpoint service must require a caller-supplied key; the shared HTTP
  client must never fabricate one.
- Generate one key for one immutable Hold-attempt snapshot.
- Preserve that exact key for:
  - the one allowed CSRF refresh retry;
  - an explicit user-requested retry of the exact same immutable attempt.
- If the selected offer, submitted stay/occupancy, or normalized contact body
  changes, the previous attempt is abandoned and a new key is required.
- Disable duplicate submission while one attempt is in flight.
- Never persist or log the raw key.

### Guest booking access token

- The one-time raw token exists only on the initial anonymous `201`.
- Capture it immediately before any later UI transition can discard the
  response.
- Retain it only in explicit in-memory active-booking state for the current
  browser tab/application lifetime.
- It must survive component rerenders and ordinary client-side navigation, but
  reload/crash recovery is intentionally not promised.
- Never store it in `localStorage`, `sessionStorage`, IndexedDB, cookies, URLs,
  query parameters, form fields, DOM attributes, logs, analytics, error
  messages, screenshots, test snapshots, or documentation.
- Never render or copy the raw token to the screen.
- If a matching in-memory session already holds a non-null token for the same
  `holdId`, a later replay body containing `guestAccessToken: null` must not
  overwrite that retained token.
- A `200` replay with no matching retained token cannot recover anonymous
  access. The UI/documentation must state this limitation honestly and must
  not imply that a replay recreates the token.
- An authenticated Hold legitimately has no guest token; do not fabricate one.
