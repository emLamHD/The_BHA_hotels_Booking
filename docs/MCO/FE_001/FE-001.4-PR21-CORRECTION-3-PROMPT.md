## 2. Confirmed remaining defect

### P2 — Fresh Availability form submission mutates local state before the authoritative gate

The second correction correctly guards `runSearch()` with
`tryBeginAvailabilitySearch()`. However,
`SectionAvailabilitySearch.handleSubmit()` still does this before that gate:

1. checks React-rendered `flowLocked`;
2. validates the current draft;
3. calls `setFieldErrors(...)`;
4. only then calls `runSearch()`, where the authoritative synchronous gate
   finally runs.

`flowLocked` is display state from the latest React render. It can remain
`false` during the same tick in which `BookingHoldFlowController.submit()` or
`retryExact()` has already set the closure-backed `inFlight` lock.

Therefore, in the Hold-first → Availability-submit same-tick order:

- the network request is correctly rejected by the gate inside `runSearch`;
- but `handleSubmit` may already clear or replace `fieldErrors`;
- if the Availability draft is invalid, `runSearch` is never called, so the
  authoritative gate is never consulted at all.

This violates the approved invariant that a rejected Availability operation
performs no local or network side effect.

## 3. Required correction

Implement the smallest coherent frontend correction. Preserve the current
provider/reducer/controller architecture and the existing two-way
serialization design.

### 3.1 Gate the form orchestration before validation and mutation

The fresh Availability form-submit path must consult a synchronous,
authoritative coordinator decision before:

- draft validation;
- `setFieldErrors(...)`;
- clearing an existing validation error;
- changing loading/error/query/result state;
- aborting/replacing a request;
- incrementing request identity;
- resetting the selected Hold offer;
- calling `searchAvailability()`.

When a Hold submit or exact retry has acquired `inFlight` in the same tick,
the Availability form submit must return after `event.preventDefault()` with
no application-state or network side effect, even when:

- the rendered `flowLocked` value is stale and still `false`;
- the current Availability draft is invalid;
- the current Availability draft is valid.

Do not solve this by moving `setFieldErrors` after the existing `runSearch`
call, by adding another rendered Boolean, by relying only on `disabled`,
or with debounce, timeout, effect, DOM timing, or a React re-render.

Use one coordinator-owned source of truth for the lock. It must include the
closure-backed same-tick `inFlight` state already used by the Hold
coordinator. Avoid duplicating phase/lock rules in unrelated components.

### 3.2 Preserve normal invalid-form semantics

Do not introduce a new regression for an ordinary unlocked invalid form
submit.

When no Hold mutation/session locks Availability:

- an invalid draft must still show the existing field errors;
- it must send zero Availability requests;
- it must not abort or replace a request;
- it must not increment request identity;
- it must not invalidate or reset a previously selected offer merely because
  validation failed.

This means the implementation must distinguish:

1. an authoritative lock rejection, which is a complete no-op; and
2. an allowed but invalid draft, which may update field-validation state but
   does not begin a search or invalidate the current offer.

A small read-only coordinator authorization method backed by the same
internal lock predicate, followed by the existing committing
`tryBeginAvailabilitySearch()` only for a valid search, is acceptable.
Another equally small design is acceptable if it preserves the two distinct
outcomes above and keeps one authoritative lock source.

### 3.3 Keep actual search commit atomic

For a valid, allowed fresh search:

- the committing Availability gate must still synchronously invalidate the
  old offer before Availability request side effects start;
- a same-tick Hold submit after the accepted search must still generate zero
  idempotency keys and zero Hold POSTs from the obsolete offer;
- the gate must be committed exactly once for the operation;
- existing ordinary-search abort/latest-request semantics must remain
  unchanged.

Do not double-dispatch `search-reset`, double-call the gate, or temporarily
release the cross-flow lock between authorization and request start.

Preserve the existing behavior of retry-search and all other Availability
entry points. If a shared helper is changed, verify every caller.

### 3.4 Use a testable orchestration seam

The current tests prove that side effects inside `runSearch` are guarded, but
they do not exercise the form-handler work that occurs before `runSearch`.

Extract the smallest React-free orchestration seam needed so the automated
test executes the same decision/order used by
`SectionAvailabilitySearch.handleSubmit`. The seam may live beside the
Availability orchestration or controller code, but must not become a second
copy of the lock rules.

Do not add jsdom, React Testing Library, Playwright, Cypress, MSW, or any new
dependency solely for this correction.
