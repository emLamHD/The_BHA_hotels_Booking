## Current backend Availability contract

The current backend exposes:

`GET /api/v1/properties/{propertyId}/availability`

Required query parameters:

- `checkIn=YYYY-MM-DD`;
- `checkOut=YYYY-MM-DD`;
- `adults`;
- `children`;
- `rooms`.

Current behavior:

- `200 OK` with a stably ordered Availability-offer array;
- `200 OK` with `[]` when the request is valid but no offer qualifies;
- RFC 7807 `400` for malformed, missing, or business-invalid inputs;
- RFC 7807 `404` when the Property does not exist or is inactive;
- no authentication is required;
- the operation is a safe `GET` and accepts none of:
  - `X-CSRF-TOKEN`;
  - `Idempotency-Key`;
  - `X-Booking-Access-Token`.

Current request rules:

- the stay range is half-open:
  `checkIn <= stayDate < checkOut`;
- `checkIn < checkOut`;
- maximum stay: 30 nights;
- `adults > 0`;
- `children >= 0`;
- `rooms > 0`;
- maximum requested rooms: 10;
- check-in may be the Property-local current date, but not an earlier date;
- occupancy eligibility is:
  `adults + children <= roomType.maxOccupancy × rooms`;
- all requested rooms in one offer use one RoomType;
- there is no mixed-RoomType allocation or child pricing.

The current `AvailabilityOfferDto` source projection contains:

- `propertyId`;
- `roomTypeId`;
- `roomTypeCode`;
- `roomTypeName`;
- nullable `roomTypeDescription`;
- `media`;
- `ratePlanId`;
- `ratePlanCode`;
- `ratePlanName`;
- `currencyCode`;
- `checkIn`;
- `checkOut`;
- `nights`;
- `requestedRooms`;
- `availableRooms`;
- `nightlyRates`, where each row contains:
  - `stayDate`;
  - `amount`;
- `totalAmount`.

Offer behavior:

- every offer is for one RoomType and one RatePlan;
- every stay night must have a real rate;
- missing nightly rates remove the offer; there is no fallback price;
- `nightlyRates` are ordered by `stayDate`;
- `currencyCode` comes from the RatePlan;
- `totalAmount` is calculated by the server;
- `availableRooms` is the minimum effective inventory across the stay after
  current inventory controls and committed demand;
- Active Holds and Confirmed Reservations are already reflected by the
  backend Availability calculation;
- Availability is still only a query-time snapshot and does not reserve a
  room.

The response does not contain or authorize:

- Property/RoomType amenities;
- PhysicalRoom ID, room number, floor, or operational status;
- internal inventory-control rows;
- individual Hold/Reservation demand;
- tax, service charge, surcharge, discount, promotion, or coupon;
- currency conversion;
- payment state;
- a promise that the offer remains available.

Treat the current generated `/swagger/v1/swagger.json`, the current backend
source, and a live response as the final authority for JSON casing, formats,
required fields, enum values, and nullability.

The repository's generated OpenAPI currently has an established nullable
reference-type convention. Do not copy the C# annotations into TypeScript by
assumption. Verify every Availability field against the generated document and
live payload. If those authorities materially contradict each other, stop and
report `BLOCKED`.
