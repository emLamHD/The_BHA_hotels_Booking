## 2. Confirmed defects

### P1-A — An unresolved request can be abandoned and a second Hold created

The current mutation state is owned by `BookingHoldPanel`, while Availability
search/offer selection is owned by `SectionAvailabilitySearch`.

While the POST is `submitting` or its outcome is `uncertain`:

- the user can still submit a new Availability search;
- the user can still select another offer;
- a new search can clear `selectedOffer`, unmount the panel, and abort the
  request;
- unmounting destroys the immutable attempt and its `Idempotency-Key`;
- the ordinary `Confirm Hold` submit remains usable in `uncertain`, creating a
  new body/key instead of forcing an exact retry.

If the server created the first Hold but the response was lost, this permits a
second Hold to be created.

### P1-B — The one-time guest token dies on client-side navigation

`activeHoldSession` is currently local `useState` in
`SectionAvailabilitySearch`. A client-side navigation away from `/home-2`
unmounts it and permanently loses the one-time guest access token.

Memory-only means **no browser persistence**, but it must still survive for
the lifetime of the mounted browser application/tab, including normal Next.js
client navigation.

## 3. Required correction

Implement the smallest coherent frontend correction that satisfies all

### 3.1 App-lifetime, per-browser memory ownership

Move authoritative Booking Hold flow state out of
`SectionAvailabilitySearch` and `BookingHoldPanel` into a client provider/store
that is mounted under `Front_End/Customer_Web/src/app/layout.tsx` and remains
mounted across App Router client navigation.

The app-lifetime state must retain, as applicable:

- the selected live-offer snapshot and its safe display label;
- the current immutable Hold attempt: exact request body plus exact
  `Idempotency-Key`;
- the submission phase;
- the active Hold session;
- the one-time `guestAccessToken`;
- the operation identity needed to reject stale completions.

Requirements:

- The provider/store must be per mounted browser app, not a module-scoped
  mutable singleton that could leak state across SSR requests or users.
- Use only React/client memory. Do not use `localStorage`, `sessionStorage`,
  IndexedDB, Cache Storage, cookies, URL/query/hash state, service workers, or
  server persistence.
- A hard reload, tab close, or browser crash may lose this state; that remains
  an explicit FE-001.4 limitation.
- The raw CSRF token, idempotency key, guest token, cookie values, and contact
  PII must never be logged, rendered, placed in URLs, or committed to tests or
  documentation.
- Clear the immutable attempt after a definitive success. Retain only the
  active session and its guest token required by later lifecycle work.
- A same-Hold `200` replay with `guestAccessToken: null` must never overwrite
  a previously retained token. A different Hold ID must never inherit a token.

The panel and Availability section must consume this authoritative state.
After navigating away and back with normal Next.js client navigation, the
flow must render the same active Hold or the same unresolved attempt without
minting a new key or issuing an automatic POST.

### 3.2 One serialized Hold mutation

Define explicit phases with equivalent semantics to:

- `idle/selected`
- `submitting`
- `known-error`
- `uncertain`
- `active-session`

Enforce all transitions in the authoritative store/coordinator, not only by
disabled button styling.

While `submitting` or `uncertain`:

- block Availability form submission;
- block `Retry last search` / `Search again`;
- block offer switching;
- block every fresh Hold submit;
- keep the selected offer and immutable attempt mounted/preserved;
- disable the relevant search, offer, contact, and fresh-submit controls with
  accessible state.

All event handlers and mutation actions must also have defensive no-op guards
so programmatic submission, rapid same-tick clicks, Enter-key submission, or a
stale render cannot bypass the disabled UI.

In `uncertain`:

- the only mutation action is `Retry exact request`;
- hide or disable the ordinary `Confirm Hold` action;
- do not generate a UUID;
- do not rebuild the request from current form fields;
- reuse the exact retained body and exact retained `Idempotency-Key`;
- do not retry automatically.

A definitive `known-error` may unlock editing and a fresh, newly keyed attempt
because the server response established that the previous attempt did not
produce an unknown outcome.

### 3.3 Synchronous in-flight and stale-result guards

React state alone is not a sufficient rapid-click guard. Add a synchronous
in-flight/attempt guard before the first `await` and before control returns to
the browser event loop.

Also assign each authoritative operation an identity/generation. A completion
may update the flow only if it still belongs to the current operation and
immutable attempt.

Prove that:

- two same-tick submits cause one UUID generation and one POST;
- a stale success cannot replace a newer/current session;
- a stale failure cannot turn a successful/current session back into
  `uncertain` or `known-error`;
- token merging reads the latest authoritative session, not a stale React
  closure;
- controller/reference cleanup occurs only for the matching operation.

Do not make `BookingHoldPanel` abort or destroy the authoritative request merely
because that panel or `/home-2` unmounted during client navigation. If an
AbortController is retained, its lifecycle must belong to the app-level
operation owner. Root-provider/app teardown may abort it.
